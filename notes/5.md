# 3. What is an Object?

Think about a real insurance policy. A policy has **data**:

```text
Policy Number
Customer
Policy Type
Sum Assured
Premium
Start Date
Expiry Date
Status
```

And it has **behavior**:

```text
calculate_premium()
renew()
cancel()
activate()
expire()
```

Therefore:  **Object = Data + Behavior** This follows the central OOP idea in the source: objects combine attributes and behaviors. 

 

# 4. What is a Class?

Suppose TFLInsurance sells 100,000 policies. Are we going to create 100,000 different programs? Of course not. We create a **Policy class**.

```text
                Policy Class
                    │
       ┌────────────┼────────────┐
       │            │            │
    Policy 1     Policy 2     Policy 3
   POL1001      POL1002      POL1003
```

The class is the **blueprint**. The objects are the actual policies. This is the same class-versus-object relationship illustrated in the source using the `Student` example. 
 

# 5. Creating a TFLInsurance Policy Class

```python
class Policy:

    def __init__(
        self,
        policy_number,
        customer_name,
        policy_type,
        premium
    ):
        self.policy_number = policy_number
        self.customer_name = customer_name
        self.policy_type = policy_type
        self.premium = premium

    def display(self):
        print(self.policy_number)
        print(self.customer_name)
        print(self.policy_type)
        print(self.premium)
```

Now create an object:

```python
policy1 = Policy( "POL1001", "Rahul", "Life",25000)
```

Another:

```python
policy2 = Policy("POL1002", "Sneha", "Health", 18000 )
```

We now have:

# 6. What is `self`?

Students often ask: **“Sir, why do we write `self`?”**

Imagine:

```python
policy1
policy2
policy3
```

Each object has its own information. When we write:

```python
self.premium
```

we are saying: **“The premium belonging to this current policy object.”** The source describes `self` as referring to the current object. 

So:

```python
policy1.premium
```

and:

```python
policy2.premium
```

can contain different values.

# 8. Encapsulation — Very Important in Insurance

Now we reach an important enterprise concept. Imagine a customer directly changing:

```text
Policy.Status
Premium.Amount
Claim.Amount
```

That would be dangerous. For example:

```text
Claim Amount = ₹50,000
```

should not become:

```text
Claim Amount = ₹5,00,000
```

because someone directly modified a property. Instead, business rules should control the change.

### Example

```python
class Claim:

    def __init__(self, claim_id, amount):
        self.__amount = amount

    def get_amount(self):
        return self.__amount

    def update_amount(self, amount):
        if amount > 0:
            self.__amount = amount
```

The data is controlled through methods. That is **encapsulation**: hide internal data and provide controlled access. 

 

# 9. TFLInsurance Claim Encapsulation

Think about claim processing:

```text
Customer
    │
    │ Submit Claim
    ▼
Claim
    │
    ▼
Validation
    │
    ▼
Claims Officer
    │
    ├── Approve
    └── Reject
```

The customer should not directly execute:

```python
claim.status = "Approved"
```

Instead:

```python
claim.submit()
claim.approve()
claim.reject()
```

The object controls its own state. That is a much better domain model.

 

# 10. Inheritance in TFLInsurance

Consider employees. We may have:

```text
Employee
   │
   ├── Agent
   ├── Manager
   ├── ClaimsOfficer
   └── AccountsOfficer
```

All are employees. Therefore, common properties can belong to:

```python
class Employee:

    def __init__(self, employee_id, name):
        self.employee_id = employee_id
        self.name = name

    def display(self):
        print(self.employee_id, self.name)
```

Then:

```python
class Agent(Employee):

    def sell_policy(self):
        print("Selling insurance policy")
```

And:

```python
class ClaimsOfficer(Employee):

    def process_claim(self):
        print("Processing claim")
```

This is **inheritance**—a specialized class reuses and extends the behavior of a general class. The source illustrates the same concept with `Person` and `Student`. 

 
# 11. Polymorphism — Same Operation, Different Behavior

Suppose TFLInsurance has different types of policies:

```text
LifePolicy
HealthPolicy
MotorPolicy
TravelPolicy
```

All may have:

```python
calculate_premium()
```

But the calculation can be different.

```python
class LifePolicy:

    def calculate_premium(self):
        return 25000
```

```python
class HealthPolicy:

    def calculate_premium(self):
        return 18000
```

```python
class MotorPolicy:

    def calculate_premium(self):
        return 12000
```

Now:

```python
policies = [
    LifePolicy(),
    HealthPolicy(),
    MotorPolicy()
]

for policy in policies:
    print(policy.calculate_premium())
```

Same method:

```text
calculate_premium()
```

Different behavior. That is **polymorphism**—one interface, multiple implementations. 

# 12. Abstraction — Hide the Complexity

Imagine a customer clicking:

> **Buy Policy**

The customer doesn't need to know:

```text
Premium calculation
Risk assessment
Database transaction
Policy number generation
Payment gateway
PDF generation
Email notification
Audit logging
```

The customer simply sees:

```text
Buy Policy
     ↓
Payment
     ↓
Policy Issued
```

The complexity is hidden behind the application interface. That is **abstraction**: expose what the user needs while hiding implementation complexity. 

 

# 13. The Four Pillars in TFLInsurance

Now we can map the four pillars directly to the insurance domain:

| OOP Principle     | TFLInsurance Example                                                 |
| ----------------- | -------------------------------------------------------------------- |
| **Encapsulation** | Claim controls how its amount/status changes                         |
| **Inheritance**   | Agent, Manager and ClaimsOfficer inherit Employee                    |
| **Polymorphism**  | Life/Health/Motor policies implement premium calculation differently |
| **Abstraction**   | Customer sees `buy_policy()` without knowing internal processing     |

The source identifies these same four pillars as the foundation of OOP.
