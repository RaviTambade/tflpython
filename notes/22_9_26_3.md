# 1. 🖥️ Start From the Computer

Before understanding Python memory management, let's understand the environment in which a Python application runs.


A Python application does not directly own the entire computer.

It runs inside a **process**, and that process operates within the environment provided by the operating system.

In simple terms:

> **An address identifies a location in memory's address space.**

Imagine a city.


Similarly, conceptually:


An object occupies memory, and the runtime uses references/pointers internally to reach objects.

# 6. ❓ What Happens When We Don't Need the Object?

Suppose:

```python

```

Now:

```text

        ↑
        X

```

If no other references reach that object, it becomes **unreachable** and eligible for memory reclamation.

# 7. 🟡 `None` Is Not a “Null Address”

This is an important correction to the classroom mental model.

In Python:

```python
policy = None
```

means the variable now refers to the singleton object `None`.

It does **not** mean:

> “Python put a special null memory address inside `policy`.”

A better mental model is:

```text
policy
   │
   ↓
None
```

rather than:

```text
policy → special empty memory address
```

This distinction becomes important when students move from C/C++ pointer concepts to Python references.

# 8. 🔗 One Object — Two References

Consider:

```python

another_policy = policy
```

How many objects?

**One.**

How many references?

**Two.**

```text
policy ─────────────┐
                    ↓
             InsurancePolicy
                    ↑
another_policy ────┘
```

This is one of the most important concepts in Python.


# 9. 🔢 Reference Counting

In CPython, object lifetime management heavily uses **reference counting**.

Conceptually:

```text
InsurancePolicy Object
        ↑
        │
     policy

Reference count = 1
```

Then:

```python
another_policy = policy
```

becomes:

```text
policy ──────────────┐
                     ↓
              InsurancePolicy
                     ↑
another_policy ──────┘

Reference count ≈ 2
```

If:

```python
policy = None
```

then:

```text
another_policy ─────→ InsurancePolicy

Reference count ≈ 1
```

If:

```python
another_policy = None
```

and no other references exist, the object becomes unreachable.

In CPython, its reference count can reach zero and its memory can then be deallocated.

# 10. 🧮 Reference Count — Classroom Demonstration

You can demonstrate reference counts in CPython with:

```python
import sys

class Policy:
    pass

policy = Policy()

print(sys.getrefcount(policy))
```

Students may see a count greater than the number of obvious references.

Why?

Because `sys.getrefcount()` itself temporarily creates another reference while evaluating its argument.

Therefore, don't teach the returned number as:

> “This is exactly the number of references in my program.”

Instead:

> **It is a diagnostic observation of the reference count in CPython, and the call itself temporarily affects that count.**

# 12. ♻️ What Does Garbage Collection Actually Do?

Here we need an important distinction.

A common classroom statement is:

> “Garbage collector checks reference count and releases memory.”

That is useful as an introduction, but it is **not the complete CPython model**.

CPython has:

1. **Reference counting**
2. **Cyclic garbage collector**

### Reference counting

Handles objects whose reference count reaches zero.

### Cyclic GC

Deals with certain **reference cycles** that cannot be reclaimed by reference counting alone.

# 13. 🔄 Circular Reference

Consider an insurance system.

A:

```text
Customer
```

has a:

```text
Policy
```

and the policy has a reference back to:

```text
Customer
```

Example:

```python
class Customer:

    def __init__(self, name):
        self.name = name
        self.policy = None


class Policy:

    def __init__(self, number):
        self.number = number
        self.customer = None
```

Create objects:

```python
customer = Customer("Ravi")
policy = Policy("P1001")

customer.policy = policy
policy.customer = customer
```

Now:

```text
       ┌─────────────────┐
       │    Customer     │
       │                 │
       └────────┬────────┘
                │
                ↓
       ┌─────────────────┐
       │     Policy      │
       │                 │
       └────────┬────────┘
                │
                │ reference back
                └──────────────→ Customer
```

We have a **cycle**.

# 14. 🔁 Why Is a Cycle a Problem?

Now:

```python
customer = None
policy = None
```

The external references disappear.

But internally:

```text
Customer ─────→ Policy
   ↑              │
   └──────────────┘
```

They still reference each other.

So simple reference counting cannot treat them as having zero references merely because the outside variables disappeared.

This is exactly why cyclic garbage detection matters.

# 15. 🗑️ Reachability Is the Bigger Idea

The most useful modern mental model is:

> **Is the object still reachable from live program references?**

Think:

```text
Live Program References
          │
          ↓
     Customer
          │
          ↓
       Policy
          │
          ↓
        Claim
```

Everything reachable through these references remains part of the live object graph.

But:

```text
No live path
     │
     ↓
Object graph
     │
     ↓
Unreachable
     │
     ↓
Potential garbage
```

# 17. 🧠 Memory Management ≠ Process Management

Two concepts should not be mixed.

### Process Management

Concerned with:

```text
Process
Threads
Scheduling
CPU
Execution
```

### Memory Management

Concerned with:

```text
Memory
Allocation
Objects
References
Object lifetime
Reclamation
```

Conceptually:

```text
Operating System
       │
 ┌─────┴───────────┐
 ↓                 ↓
Process Mgmt.    Memory Mgmt.
 ↓                 ↓
CPU / Threads     Virtual Memory
```

Python additionally has its own runtime-level mechanisms for managing Python objects.

# 18. 🧩 Manual vs Automatic Memory Management

### C/C++

Developers can explicitly manage dynamically allocated memory:

```cpp
Complex* p = new Complex();

delete p;
```

### Java

No normal equivalent of:

```text
delete object
```

for ordinary objects.

### Python

Similarly, developers normally don't write:

```text
free(policy)
```

to release Python objects.

Instead:

```python
policy = None
```

removes that particular reference.

The runtime manages object lifetime and memory reclamation.

# 19. 🚫 Don't Teach `None` as `free()`

This is another important distinction.

This:

```python
policy = None
```

does **not** mean:

```text
free(policy)
```

It means:

```text
Remove the reference from variable `policy`
```

Then the runtime determines what happens to the previously referenced object based on the remaining references and garbage-collection mechanisms.

# 22. 🧪 Hands-On Lab

## Lab: Understand Object References

```python
class Policy:

    def __init__(self, number):
        self.number = number

    def __str__(self):
        return self.number


policy1 = Policy("P1001")

policy2 = policy1

print(policy1)
print(policy2)

policy1 = None

print(policy2)

policy2 = None
```

### Ask Students

**Q1. How many `Policy` objects were created?**

Answer:

```text
One
```

**Q2. How many references initially point to it?**

```text
Two
```

**Q3. Does `policy2 = policy1` create another object?**

```text
No.
```

**Q4. What happens after:**

```python
policy1 = None
```

`policy2` still refers to the same object.

**Q5. What happens after:**

```python
policy2 = None
```

If no other references exist, the object becomes unreachable.


# 23. 🧪 Hands-On Lab — Circular Reference

```python
class Customer:

    def __init__(self, name):
        self.name = name
        self.policy = None


class Policy:

    def __init__(self, number):
        self.number = number
        self.customer = None


customer = Customer("Ravi")
policy = Policy("P1001")

customer.policy = policy
policy.customer = customer

customer = None
policy = None
```

Ask:

> **“External references गेल्या. पण Customer आणि Policy objects मध्ये काय relationship आहे?”**

Draw:

```text
Customer ─────────→ Policy
    ↑                 │
    └─────────────────┘
```

This is the foundation for understanding **circular garbage collection**.

# 🌸 Transflower Mentor Takeaway

> **“Variable is not the object.
> Variable holds a reference to the object.”**
>
> **“`None` is not `free()`.”**
>
> **“Reference disappears → object may become unreachable.”**
>
> **“Unreachable object → eligible for reclamation.”**
>
> **“Reference counting handles a major part of CPython's memory management; cyclic GC handles reference cycles.”**

And the bigger lesson:

```text
Don't just ask:
"How do I write this Python code?"

Ask:
"After I write it, how does Python execute it,
where does the object live,
who references it,
how long does it live,
and how is its memory eventually reclaimed?"
```

> **That is when Python stops being just a programming language and starts becoming Computer Science.**
