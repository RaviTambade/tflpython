# Operator Overloading in Python — Using TFLInsurance

> *“Don't learn `__add__()` as syntax. First ask: What does `+` mean in our business domain?”*

Imagine we are developing **TFLInsurance**, an insurance management application. Our system contains different business objects:

* Customer
* Agent
* Insurance Product
* Policy
* Premium
* Claim
* Nominee

Now imagine the insurance manager asks us:  **Manager:** “Can I combine two insurance policies and get a summary of their total coverage?” A developer may initially write:

```python
total_coverage = policy1.coverage + policy2.coverage
```

That works. But suppose we want our business objects themselves to understand `+`:

```python
combined_policy = policy1 + policy2
```

Now we have an interesting question: **How can Python understand what `+` means when the operands are Policy objects?** This is where **Operator Overloading** enters the picture.

 

# 1. What is Operator Overloading?

Normally Python already knows what operators mean.

```python
10 + 20
```

means:

```text
30
```

And:

```python
"Hello " + "Ravi"
```

means:

```text
Hello Ravi
```

The same `+` operator behaves differently depending upon the objects involved. This is **operator overloading**. In simple words:**Operator overloading means defining meaningful behavior for standard operators when they are used with our own objects.** Python provides special methods, commonly called **dunder methods**, to implement this behavior.

For example:

| Operator | Dunder Method | Meaning               |
| -------- | ------------- | --------------------- |
| `+`      | `__add__()`   | Addition              |
| `-`      | `__sub__()`   | Subtraction           |
| `*`      | `__mul__()`   | Multiplication        |
| `==`     | `__eq__()`    | Equality              |
| `<`      | `__lt__()`    | Less than             |
| `>`      | `__gt__()`    | Greater than          |
| `str()`  | `__str__()`   | String representation |
| `len()`  | `__len__()`   | Length                |

# 5. Now Comes the Interesting Part — `+`

Suppose we write:

```python
policy1 + policy2
```

Python doesn't automatically know what addition means for our `InsurancePolicy` objects. So we define:

```python
def __add__(self, other):
```

Inside the class:

```python
class InsurancePolicy:

    def __init__(self, policy_id, customer, coverage):
        self.policy_id = policy_id
        self.customer = customer
        self.coverage = coverage

    def __str__(self):
        return (
            f"Policy({self.policy_id}, "
            f"Customer: {self.customer}, "
            f"Coverage: ₹{self.coverage})"
        )

    def __add__(self, other):

        if isinstance(other, InsurancePolicy):

            combined_coverage = (
                self.coverage + other.coverage
            )

            return InsurancePolicy(
                "COMBINED",
                self.customer,
                combined_coverage
            )

        return NotImplemented
```

 

# 6. Now Let's Use It

```python
policy1 = InsurancePolicy( "POL1001", "Ravi", 1000000)
policy2 = InsurancePolicy( "POL1002","Ravi",500000)
combined_policy = policy1 + policy2
print(combined_policy)
```

Output:

```text
Policy(COMBINED, Customer: Ravi, Coverage: ₹1500000)
```

Look carefully. We wrote:

```python
policy1 + policy2
```

But Python internally invokes:

```python
policy1.__add__(policy2)
```

Conceptually:

```text
policy1 + policy2
       │
       ▼
policy1.__add__(policy2)
       │
       ▼
combined policy
       │
       ▼
₹10,00,000 + ₹5,00,000
       │
       ▼
₹15,00,000
```

# 8. Why `isinstance()`?

Notice this code:

```python
if isinstance(other, InsurancePolicy):
```

Why? Because we don't want meaningless operations. For example:

```python
policy1 + 100
```

- What does that mean?
- Should we add ₹100 to the policy?
- Should we increase coverage?
- Should we increase premium?

The meaning is unclear.

Therefore our implementation says:

```python
if isinstance(other, InsurancePolicy):
    ...
```

Otherwise:

```python
return NotImplemented
```

This is important.  **Operator overloading should represent a meaningful business operation, not merely a clever programming trick.**

 

# 9. `==` — Comparing Insurance Policies

Now let's ask another business question. Suppose the system needs to determine: “Are these two policies the same?” We can overload:

```python
__eq__()
```

Example:

```python
def __eq__(self, other):

    if isinstance(other, InsurancePolicy):
        return self.policy_id == other.policy_id

    return NotImplemented
```

Now:

```python
policy1 == policy2
```

internally behaves conceptually like:

```python
policy1.__eq__(policy2)
```

For example:

```python
policy1 = InsurancePolicy(
    "POL1001",
    "Ravi",
    1000000
)

policy2 = InsurancePolicy(
    "POL1002",
    "Ravi",
    500000
)

print(policy1 == policy2)
```

Output:

```text
False
```

# 11. Complete TFLInsurance Example

Let's bring everything together.

```python
class InsurancePolicy:

    def __init__(self, policy_id, customer, coverage):
        self.policy_id = policy_id
        self.customer = customer
        self.coverage = coverage

    def __str__(self):
        return (
            f"Policy({self.policy_id}, "
            f"Customer: {self.customer}, "
            f"Coverage: ₹{self.coverage})"
        )

    # + operator
    def __add__(self, other):

        if isinstance(other, InsurancePolicy):

            combined_coverage = (
                self.coverage + other.coverage
            )

            return InsurancePolicy(
                "COMBINED",
                self.customer,
                combined_coverage
            )

        return NotImplemented

    # == operator
    def __eq__(self, other):

        if isinstance(other, InsurancePolicy):
            return self.policy_id == other.policy_id

        return NotImplemented

    # < operator
    def __lt__(self, other):

        if isinstance(other, InsurancePolicy):
            return self.coverage < other.coverage

        return NotImplemented

    # > operator
    def __gt__(self, other):

        if isinstance(other, InsurancePolicy):
            return self.coverage > other.coverage

        return NotImplemented
```

Usage:

```python
policy1 = InsurancePolicy("POL1001", "Ravi", 1000000)
policy2 = InsurancePolicy("POL1002", "Ravi", 500000)

print(policy1)
print(policy2)

print("\nCombined Policy:")
combined = policy1 + policy2
print(combined)

print("\nComparison:")
print("Same policy:", policy1 == policy2)
print("Policy1 < Policy2:", policy1 < policy2)
print("Policy1 > Policy2:", policy1 > policy2)
```

# 13. Another Interesting Example — Premium

Suppose TFLInsurance has:

```python
class Premium:
```

Business says: “Add two premium amounts.” We could implement:

```python
def __add__(self, other):
```

Then:

```python
premium1 = Premium(25000)
```

Conceptually:

```text

```

Again, the object knows how to participate in the operation.

 

# 14. A Very Important Design Question

Here I would challenge the students: 
> **Mentor:** “Can we overload every operator?”

Technically Python provides many special methods. But should we? **No.** Operator overloading should be used only when the meaning is:

1. **Natural**
2. **Understandable**
3. **Consistent**
4. **Useful in the domain**

For example:

```python
policy1 + policy2
```

may be understandable if our application explicitly defines it as a coverage aggregation. But inventing something strange like:

```python
policy1 * policy2
```

without a clear business meaning would make the code confusing.
