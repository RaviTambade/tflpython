# 🛡️ Python Exception Handling

Mentor says: “Friends, errors are not the enemy. An unexpected error is a business event that our software must learn to handle gracefully.” Imagine a customer is paying an insurance premium. Everything works perfectly:

```text
Customer
   ↓
Select Policy
   ↓
Enter Premium
   ↓
Payment
   ↓
Policy Renewed
```

But what happens if:

* customer enters `"abc"` instead of an amount?
* policy number doesn't exist?
* premium amount is negative?
* database is unavailable?
* payment gateway fails?

Our application should **not suddenly crash**. That's where **Exception Handling** comes in.

 

# 1️⃣ What is an Exception?

An exception is an **unexpected condition during program execution** that interrupts the normal flow of the program.

For example:

```python
age = int(input("Enter age: "))
```

Suppose the user enters:

```text
twenty
```

Python cannot convert `"twenty"` into an integer. You get something like:

```text
ValueError
```

Without handling it, the program terminates.

 

# 2️⃣ TFLInsurance Example

Suppose we have:

```python
premium = int(input("Enter premium amount: "))

print("Premium:", premium)
```

User enters:

```text
25000
```

Everything is fine.

But suppose:

```text
Enter premium amount: abc
```

Python raises:

```text
ValueError
```

Our application stops. As a mentor, I ask: **“Should an insurance application crash just because a customer entered invalid input?”** Of course not. We need a recovery mechanism.

 

# 3️⃣ `try` and `except`

Python provides:

```python
try:
    # risky code
except:
    # error handling code
```

Let's modify our example:

```python
try:
    premium = int(input("Enter premium amount: "))
    print("Premium:", premium)

except:
    print("Invalid premium amount.")
```

Now:

```text
Enter premium amount: abc
Invalid premium amount.
```

The application doesn't crash.

 

# 4️⃣ Understand the Flow

Think of `try` like this: **“Python, try to execute this business operation.”** And `except` means: **“If something goes wrong, come here and handle it.”**

```text
             try
              │
              ▼
       Execute operation
              │
        ┌─────┴─────┐
        │           │
      Success      Error
        │           │
        ▼           ▼
     Continue     except
                    │
                    ▼
              Handle problem
```

 
# 5️⃣ Don't Use a Generic `except` Everywhere

This is not a good practice:

```python
try:
    premium = int(input("Enter premium: "))

except:
    print("Something went wrong")
```

Why? Because we don't know **what went wrong**. Instead, catch the expected exception.

```python
try:
    premium = int(input("Enter premium: "))

except ValueError:
    print("Please enter a valid numeric premium.")
```

Much better.

 

# 6️⃣ TFLInsurance — Premium Validation

Let's build a small example.

```python
try:

    premium = float(input("Enter annual premium: "))

    if premium <= 0:
        raise ValueError("Premium must be greater than zero.")

    print("Premium accepted:", premium)

except ValueError as ex:

    print("Invalid premium:", ex)
```

Now there are two possible problems:

### Invalid text

```text
Enter annual premium: abc
```

Result:

```text
Invalid premium: could not convert string to float
```

### Invalid amount

```text
Enter annual premium: -5000
```

Result:

```text
Invalid premium: Premium must be greater than zero.
```

This is a very important software-engineering idea:

> **Input validation protects the business rules.**

 

# 7️⃣ `raise` — Creating Our Own Exception

Sometimes Python doesn't automatically know that something is wrong from the **business perspective**. For example:

```python
premium = -5000
```

Python itself has no problem storing `-5000`.

But TFLInsurance says: Premium cannot be negative. So we can explicitly raise an exception:

```python
if premium <= 0:
    raise ValueError("Premium must be greater than zero.")
```

The `raise` keyword allows us to signal an error condition ourselves.

 
# 8️⃣ Multiple Exceptions

Suppose our application performs:

```python
age = int(input("Enter age: "))
```

and then accesses some collection. Different problems can occur. We can handle different exception types:

```python
try:

    age = int(input("Enter age: "))

except ValueError:
    print("Age must be a number.")

except TypeError:
    print("Invalid data type.")
```

Each exception can have its own recovery strategy.

 

# 9️⃣ `else` — What If Everything Works?

Python also provides `else`.

```python
try:
    premium = float(input("Enter premium: "))

except ValueError:
    print("Invalid premium.")

else:
    print("Premium accepted.")
```

The `else` block executes **only when the `try` block succeeds without an exception**.

Think:

```text
try
 │
 ├── Error → except
 │
 └── Success → else
```

 

# 🔟 `finally` — Always Execute

Now imagine TFLInsurance is communicating with a database. We might conceptually have:

```python
try:
    print("Opening database connection...")
    # database operation

except Exception:
    print("Database operation failed.")

finally:
    print("Closing database connection...")
```

Whether the operation succeeds or fails:

```text
finally
```

runs. This makes `finally` useful for **cleanup operations** such as releasing resources.

 

# 1️⃣1️⃣ Complete Structure

Python exception handling can look like:

```python
try:

    # risky operation

except SomeException:

    # handle error

else:

    # executed when no exception occurs

finally:

    # cleanup
```

Mentor memory trick:

> **TRY → EXCEPT → ELSE → FINALLY**

  

# 1️⃣2️⃣ TFLInsurance Payment Example

Imagine a payment service.

```python
def pay_premium(amount):

    try:

        amount = float(amount)

        if amount <= 0:
            raise ValueError("Payment amount must be positive.")

        print("Processing payment...")
        print("Payment successful.")

    except ValueError as ex:

        print("Payment failed:", ex)

    finally:

        print("Payment operation completed.")
```

Call:

```python
pay_premium(25000)
```

Output:

```text
Processing payment...
Payment successful.
Payment operation completed.
```

But:

```python
pay_premium(-500)
```

Output:

```text
Payment failed: Payment amount must be positive.
Payment operation completed.
```
  

# 1️⃣3️⃣ Real Insurance Example — Policy Not Found

Suppose:

```python
policies = {
    "POL1001": "Life Insurance",
    "POL1002": "Health Insurance"
}
```

Customer enters:

```text
POL9999
```

We could raise our own exception:

```python
def get_policy(policy_number):

    if policy_number not in policies:
        raise KeyError(
            f"Policy {policy_number} does not exist."
        )

    return policies[policy_number]
```

Then:

```python
try:

    policy = get_policy("POL9999")
    print(policy)

except KeyError as ex:

    print("Policy error:", ex)
```

Output:

```text
Policy error: 'Policy POL9999 does not exist.'
```

Now our code is beginning to represent **real business behavior**.

# 1️⃣4️⃣ Custom Exceptions

In a larger TFLInsurance application, generic exceptions may not communicate enough business meaning. We can create our own exception.

```python
class PolicyNotFoundException(Exception):
    pass
```

Then:

```python
def get_policy(policy_number):

    if policy_number not in policies:
        raise PolicyNotFoundException(
            f"Policy {policy_number} was not found."
        )

    return policies[policy_number]
```

And:

```python
try:

    policy = get_policy("POL9999")

except PolicyNotFoundException as ex:

    print(ex)
```

Now the exception itself communicates the business meaning:

```text
PolicyNotFoundException
```

rather than just:

```text
Exception
```

 

# 1️⃣5️⃣ Why Custom Exceptions Matter

Imagine an enterprise insurance application has:

```text
PolicyNotFoundException
CustomerNotFoundException
ClaimNotFoundException
InvalidPremiumException

PolicyExpiredException
UnauthorizedClaimException
```

Now developers can understand what happened. Compare:

```python
except Exception:
    print("Something went wrong")
```

with:


The second one speaks the **language of the business**. That is what we want in domain-driven software.

 

# 1️⃣6️⃣ Exception Handling Is Not Validation

This is an important distinction.

### Validation

We check whether input is acceptable.

```python
if premium <= 0:
    print("Invalid premium")
```

### Exception Handling

We handle an exceptional situation.

```python
try:
    premium = float(input("Premium: "))

except ValueError:
    print("Invalid numeric input.")
```

So:

```text
Validation
    ↓
Is this data acceptable?

Exception Handling
    ↓
What should we do when something goes wrong?
```

They work together.

 

# 1️⃣7️⃣ Don't Hide Errors

Avoid writing:

```python
try:
    process_claim()

except:
    pass
```

This is dangerous. The program silently ignores the problem. Imagine:

```text
Claim submitted
     ↓
Database error
     ↓
except
     ↓
pass
     ↓
Application continues
```

Now nobody knows that the claim was never saved. That can create serious business problems.

 

# 1️⃣8️⃣ Logging Instead of Just Printing

In a real TFLInsurance application, we may want:

```text
INFO     Claim submitted
INFO     Payment initiated
ERROR    Payment gateway unavailable
ERROR    Database connection failed
```

Instead of only:

```python
print("Something went wrong")
```

we use logging. Conceptually:

```python
import logging

logging.error("Payment processing failed")
```

This becomes especially important in production systems.

A mature application shouldn't expose internal technical details directly to the customer. Instead:

# 🌸 Mentor's Golden Rule

> **“Exception handling is not about hiding errors. It is about handling errors responsibly.”**

A good engineer asks three questions:

### 1. What can go wrong?

```text
Invalid input
Database failure
Network failure
Missing policy
Payment failure
```

### 2. How should the application respond?

```text
Retry
Show message
Return appropriate response
Log
Recover
```

### 3. What should the customer see?

Not:

```text

DatabaseException...
```

But something meaningful:

```text
Policy not found.
Payment failed.
Policy has expired.
Please enter a valid premium.
```
