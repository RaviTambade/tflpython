# 🐍 Python Garbage Collection — Part 3

## Circular References, Generational GC & `gc.collect()`

> **“A great programmer does not only understand how objects are created.
> A great programmer understands how objects become unreachable and how their memory is reclaimed.”**

This session takes the previous **Customer–Policy** example one level deeper.

---

# 1. 🔄 Customer–Policy Mutual Dependency

Consider our insurance application.

A `Customer` can have a `Policy`.

A `Policy` belongs to a `Customer`.

```python
class Customer:

    def __init__(self, name):
        self.name = name
        self.policy = None


class Policy:

    def __init__(self, number):
        self.number = number
        self.customer = None
```

Create objects:

```python
customer = Customer("Ravi")
policy = Policy("P1001")
```

Now establish the relationship:

```python
customer.policy = policy
policy.customer = customer
```

The object graph becomes:

```text
        ┌─────────────────┐
        │    Customer     │
        │                 │
        │ policy ─────────┼──────┐
        └─────────────────┘      │
              ↑                  ↓
              │          ┌─────────────────┐
              │          │     Policy      │
              └──────────┤ customer        │
                         └─────────────────┘
```

We have created a **circular reference**.

---

# 2. 🧠 Dependency vs Reference

Students often use the word **dependency** loosely.

There are two related but different ideas:

### Dependency

One component needs another component to perform its work.

```text
PolicyService
      ↓
CustomerRepository
```

### Object reference

One object actually holds a reference to another object.

```text
Customer Object
      │
      ↓
Policy Object
```

In our example, the objects have **mutual references**:

```text
Customer ─────→ Policy
    ↑             │
    └─────────────┘
```

This is the important memory-management problem.

---

# 3. 🔗 Circular Reference

Let's simplify the example:

```python
customer.policy = policy
policy.customer = customer
```

Think of it as:

```text
Customer
   │
   │ reference
   ↓
Policy
   │
   │ reference
   └──────────────→ Customer
```

This is called a:

> **Circular reference / reference cycle**

---

# 4. 🚨 What Happens When Variables Disappear?

Now execute:

```python
customer = None
policy = None
```

A beginner may think:

> “Both objects are gone.”

Not necessarily.

Look carefully.

The variables are gone as external references, but the objects can still reference one another:

```text
        Customer
           │
           ↓
        Policy
           │
           ↓
        Customer
```

There is still a cycle.

Conceptually:

```text
External References
       │
       X

Customer ─────→ Policy
    ↑             │
    └─────────────┘
```

---

# 5. 🔢 Why Reference Counting Alone Is Not Enough

Suppose:

```text
Customer → Policy
   ↑         │
   └─────────┘
```

Even after the external references disappear:

```text
Customer
   ↑     │
   │     ↓
   └── Policy
```

each object may still have an incoming reference from the other object.

Therefore, **reference counting alone cannot simply say:**

```text
"Reference count is zero."
```

The objects form an unreachable cycle.

This is why CPython has a **cyclic garbage collector** in addition to reference counting.

---

# 6. ♻️ Cyclic Garbage Collector

CPython's memory-management model can be simplified as:

```text
                Python Object Memory
                       │
             ┌─────────┴─────────┐
             ↓                   ↓
      Reference Counting    Cyclic GC
             │                   │
             ↓                   ↓
      Count reaches 0       Detect cycles
             │                   │
             ↓                   ↓
       Reclaim object      Reclaim unreachable
                              cycles
```

### Mentor Statement

> **Reference counting handles objects whose reference count reaches zero.
> Cyclic GC helps detect unreachable reference cycles.**

---

# 7. 🧭 Reachability — The Bigger Concept

Instead of asking only:

> “What is the reference count?”

ask:

> **“Can the object still be reached by the running program?”**

Example:

```text
Program Root
     │
     ↓
 Customer
     │
     ↓
 Policy
     │
     ↓
 Claim
```

These objects are reachable.

But:

```text
Program Root

Customer ←────→ Policy
```

with no path from the live program to the cycle means:

```text
Unreachable cycle
       ↓
Potential garbage
       ↓
Cyclic GC
       ↓
Memory reclamation
```

# 8. 🏫 Ravi Sir's Classroom Analogy

Imagine a college classroom.

```text
Front Bench
     ↓
Students who are actively participating

Second Bench
     ↓
Students participating occasionally

Back Bench
     ↓
Students who are less engaged
```

Sir doesn't continuously stop teaching to count every student.

Why?

Because that would waste the main resource:

> **His teaching time.**

Similarly, a garbage collector cannot afford to perform expensive complete inspection of every object after every operation.

It uses strategies to make memory management practical.

---

# 9. 🧬 Generational Garbage Collection

A common garbage-collection principle is:

> **Most objects die young.**

Applications continuously create temporary objects.

For example:

```python
def calculate_premium():
    result = 10000
    return result
```

Objects created during short-lived operations may become unreachable quickly.

Other objects live much longer:

```text
Application configuration
Database connection state
Long-lived service objects
Caches
```

Therefore, treating every object identically can be inefficient.

---

# 10. 🧓 Young vs Long-Lived Objects

Imagine students entering college:

```text
New Students
     ↓
First Year
     ↓
Second Year
     ↓
Final Year
```

Similarly, conceptually:

```text
New Objects
     ↓
Young Generation
     ↓
Surviving Objects
     ↓
Older Generation
```

The idea is:

```text
New object
   │
   ↓
Survives collection
   │
   ↓
Survives again
   │
   ↓
Considered long-lived
```

---

# 11. ⚠️ Python Generation Terminology

One important correction for teaching accuracy:

The generational garbage collector terminology in **modern CPython is generation 0, generation 1, and generation 2**.

Conceptually:

```text
Generation 0
    ↓
Generation 1
    ↓
Generation 2
```

You may hear people describe these as:

```text
Young
Middle
Old
```

or informally as:

```text
Generation 1
Generation 2
Generation 3
```

but for Python/CPython teaching, use the actual terminology:

> **Generation 0, Generation 1, Generation 2**

---

# 12. 🥇 Generation 0

Newly tracked objects begin in the youngest generation.

```text
New Objects
     ↓
Generation 0
```

This generation is collected relatively frequently.

Why?

Because many newly created objects become unnecessary quickly.

---

# 13. 🥈 Generation 1

Objects that survive collections can move/promote into an older generation.

Conceptually:

```text
Generation 0
     │
     │ survives
     ↓
Generation 1
```

The collection frequency becomes lower.

---

# 14. 🥉 Generation 2

Longer-lived objects can eventually be promoted further.

```text
Generation 0
     ↓
Generation 1
     ↓
Generation 2
```

Generation 2 contains older objects that have survived previous collection cycles.

---

# 15. ⚡ Why Generations Improve Performance

Imagine having:

```text
1,000,000 objects
```

If the collector performs an expensive inspection of everything every time:

```text
1,000,000 objects
        ↓
Inspect everything
        ↓
Expensive
```

Instead, it can focus more frequently on younger objects.

```text
Generation 0
   ↓
small/young population
   ↓
frequent inspection

Generation 1
   ↓
less frequent

Generation 2
   ↓
even less frequent
```

The exact collection behavior is implementation-specific, but the underlying principle is:

> **Don't spend equal effort on objects with very different expected lifetimes.**

---

# 16. 🧠 Insurance Application Analogy

Suppose TFL Insurance creates:

```text
10,000 temporary calculation objects
```

and:

```text
5,000 long-lived application objects
```

Many calculation objects may exist only for milliseconds or seconds.

Conceptually:

```text
Premium calculation
       ↓
Temporary objects
       ↓
No longer required
       ↓
Garbage
```

While:

```text
Application configuration
       ↓
Long-lived object
       ↓
Still reachable
       ↓

```

Generational strategies exploit this difference in object lifetimes.

# 17. 🛠️ Python `gc` Module

Python provides the `gc` module for interacting with its cyclic garbage collector.

```python
import gc
```

You can explicitly request a collection with:

```python
gc.collect()
```

Example:

```python
import gc

print("Requesting garbage collection...")

collected = gc.collect()

print("Objects collected:", collected)
```

---

# 18. ⚠️ What Does `gc.collect()` Mean?

This is important.

When you write:

```python
gc.collect()
```

you are essentially asking Python's cyclic garbage collector to perform a collection.

It does **not** mean:

```text
Delete every object
```

Nor:

```text
Free all memory
```

Only objects eligible for collection can be reclaimed.

Reachable objects remain alive.

---

# 19. 🧪 Demonstration of Circular References

Try:

```python
import gc


class Customer:

    def __init__(self, name):
        self.name = name
        self.policy = None


class Policy:

    def __init__(self, number):
        self.number = number
        self.customer = None


customer = Customer("Ravi")
policy = Policy("P1001")

customer.policy = policy
policy.customer = customer

customer = None
policy = None

print("Requesting GC...")

collected = gc.collect()

print("Collected:", collected)
```

This demonstrates the idea of explicitly requesting cyclic garbage collection.

The exact number returned can vary with the Python version and runtime state, so don't build the lesson around a fixed numeric result.

---

# 20. 🔍 Inspecting the Garbage Collector

You can inspect GC status:

```python
import gc

print(gc.get_count())
```

You can also inspect thresholds:

```python
print(gc.get_threshold())
```

And check whether automatic GC is enabled:

```python
print(gc.isenabled())
```

These are useful for experimentation and understanding runtime behavior.

---

# 21. 🧠 `gc.collect()` Is Not a Normal Business Operation

Don't write application code like:

```python
def process_policy():

    # business logic

    gc.collect()

    # more business logic
```

everywhere.

Garbage collection is a runtime concern, not normally part of your business logic.

Use the `gc` module mainly when:

* learning how GC works
* diagnosing memory behavior
* investigating reference cycles
* performing controlled runtime experiments

---

# 22. 🏗️ Avoid Unnecessary Circular References

A useful software-design lesson is:

> **Don't create bidirectional object references unless they genuinely serve the domain model or application behavior.**

Instead of:

```text
Customer ↔ Policy
```

sometimes your design can use:

```text
Customer
   │
   ↓
Policy ID
```

or:

```text
Policy
   │
   ↓
Customer ID
```

or a repository/service relationship:

```text
Customer
   │
   ↓
PolicyService
   │
   ↓
PolicyRepository
```

The correct choice depends on the application's domain and requirements.

---

# 23. 🗄️ Database Circular Relationships

The same thinking appears in databases.

Suppose:

```text
Customer
   │
   ↓
Policy
```

and:

```text
Policy
   │
   ↓
Customer
```

Foreign keys can represent relationships, but database relationships and Python object references are **not the same thing**.

A database may have:

```text
Customer
---------
customer_id
name
```

and:

```text
Policy
---------
policy_id
customer_id
policy_number
```

Here:

```text
Policy.customer_id
        │
        ↓
Customer.customer_id
```

This represents a relationship without requiring the Python objects themselves to hold strong references to each other.

# 25. 🧑‍🏫 Classroom Questions

### Question 1

```python
policy2 = policy1
```

Does this create another object?

**Answer:** No. It creates another reference to the same object.

---

### Question 2

```python
policy1 = None
```

Does it immediately destroy the object?

**Answer:** Not necessarily. It removes one reference.

---

### Question 3

When can an object become garbage?

**Answer:** When it is no longer reachable by the running program.

---

### Question 4

Why isn't reference counting alone sufficient?

**Answer:** Because reference cycles can keep objects referencing one another even when the cycle is unreachable from the rest of the program.

---

### Question 5

What helps CPython deal with such cycles?

**Answer:** Its cyclic garbage collector.

---

### Question 6

What does:

```python
gc.collect()
```

do?

**Answer:** It explicitly requests a garbage-collection cycle; it doesn't mean “delete all objects.”

> **Don't worship the garbage collector. Understand object lifetime.**
>
> **Don't manually force GC without a reason.**
>
> **Design object relationships carefully.**
>
> **And always learn from first principles:**
>
> **Computer → OS → Process → Runtime → Memory → Object → Reference → Reachability → Garbage Collection.**

That mental model will help students understand not only Python, but also **Java, .NET, JavaScript/Node.js and other managed-runtime technologies**.
