# 1. Mentor Opening

**Ravi Sir:**

> Students, today I want to introduce one very important concept. We are building an Insurance application.  We have something called a **Policy**.  Now the question is: **How should we represent a Policy inside our Python application?**

A beginner may immediately write:

```python
policy = {
    "id": 1,
    "name": "Jeevan Labh",
    "description": "Life insurance savings plan",
    "maturity": "10 years",
    "premium": 15000
}
```

It works. But as our application grows, we don't want to keep passing dictionaries everywhere. So we introduce **classes**.

```text
                Insurance Policy
                       |
                       v
                 Python Object
                       |
             +---------+---------+
             |                   |
        Dataclass           Pydantic Model
```


# 2. First Question — What is a Class?

A class gives us a structure for representing an object.

```python
class Policy:
    pass
```

Now we can create:

```python
policy = Policy()
```

But we need to store data.

```python
class Policy:

    def __init__(
        self,
        id,
        name,
        description,
        maturity,
        premium
    ):
        self.id = id
        self.name = name
        self.description = description
        self.maturity = maturity
        self.premium = premium
```

This works. But look at the amount of code. For a simple data object, Python gives us a better option.


# 3. Python Dataclass

```python
from dataclasses import dataclass

@dataclass
class Policy:

    id: int
    name: str
    description: str
    maturity: str
    premium: float
```

That's it. Python automatically generates much of the boilerplate for us, including an appropriate constructor. Now:

```python
policy = Policy( 1, "Jeevan Labh", "Life insurance savings plan", "10 years", 15000 )
```

We can access:

```python
print(policy.name)
print(policy.premium)
```

Output:

```text
Jeevan Labh
15000
```


# 4. What is the Purpose of Dataclass?

**Ravi Sir:**

> Don't think of a dataclass as something magical. Think of it as a convenient way to create a class whose primary purpose is to **hold related data**.

For example:

```text
Policy
 |
 +-- id
 +-- name
 +-- description
 +-- maturity
 +-- premium
```

Instead of carrying five separate variables:

```text
id
name
description
maturity
premium
```

we carry one object:

```text
Policy
```

This is **object-oriented thinking**.


# 5. But Now We Have an API

Suppose our React application sends:

```http
POST /api/policies
```

with:

```json
{
    "name": "Jeevan Labh",
    "description": "Life insurance savings plan",
    "maturity": "10 years",
    "premium": 15000
}
```

Now we have another problem. **How do we make sure that this incoming data is valid?**

For example:

```json
{
    "name": "",
    "description": "Life insurance",
    "maturity": "10 years",
    "premium": -5000
}
```

Should our application accept this? Obviously not. Now we need **validation**. This is where Pydantic enters the picture.



# 6. Pydantic Model

```python
from pydantic import BaseModel, Field

class PolicyCreate(BaseModel):

    name: str = Field(min_length=2,  max_length=100 )
    description: str = Field( min_length=2, max_length=100 )
    maturity: str
    premium: float = Field(gt=0)
```

Now Pydantic understands our rules.

```text
PolicyCreate
     |
     +-- name
     |    +-- string
     |    +-- minimum 2 characters
     |    +-- maximum 100 characters
     |
     +-- description
     |
     +-- maturity
     |
     +-- premium
          |
          +-- must be greater than 0
```

# 7. What Does Pydantic Do?

Think of Pydantic as a **gatekeeper**.

```text
             Client
               |
               | JSON
               v
       +---------------+
       |    FastAPI    |
       +-------+-------+
               |
               v
       +---------------+
       |    Pydantic   |
       |   Validation  |
       +-------+-------+
               |
        +------+------+
        |             |
      Valid        Invalid
        |             |
        v             v
     Service       HTTP 422
```

The Pydantic model answers: **"Is the data coming into my application valid according to my contract?"**


# 8. Dataclass vs Pydantic

Now students usually ask:

> Sir, both are Python classes. Why do we need both?

Excellent question. The answer is:

### They have different responsibilities.

```text
Dataclass
   |
   +-- Represent application/domain data
   +-- Convenient data container
   +-- Reduce boilerplate


Pydantic Model
   |
   +-- Validate data
   +-- Define API contract
   +-- Parse/serialize data
   +-- Work naturally with FastAPI
```


# 9. Think About a Security Guard

**Ravi Sir:**

> Imagine Transflower campus.  A student comes to the gate.  We don't simply allow anybody to enter.  There is a security check. 

Similarly:

```text
JSON Request
     |
     v
+-------------+
|   Pydantic  |
|   Gatekeeper|
+-------------+
     |
     | Valid

     |

```

Pydantic says:

> "First prove that your data is valid."

> "Now I will represent this data inside my application."


# 10. Why Separate PolicyCreate and PolicyResponse?

Now let's go one step further. For creating a policy:

```python
class PolicyCreate(BaseModel):

    name: str
    description: str
    maturity: str
    premium: float
```

Notice:

```text
No ID
```

Why? Because the client should not decide the database ID.

```text
Client
   |
   | Policy details
   v
FastAPI
   |
   | Generate ID
   v
Database
```

But when we return the policy:

```json
{
    "id": 1,
    "name": "Jeevan Labh",
    "description": "Life insurance savings plan",
    "maturity": "10 years",
    "premium": 15000
}
```

Now we need `id`. So:

```python
class PolicyResponse(PolicyCreate):
    id: int
```

Now we have:

```text
                Policy
                  |
       +----------+----------+
       |          |          |
     Create     Update     Response
       |          |          |
 PolicyCreate PolicyUpdate PolicyResponse
       |          |          |
     INPUT      INPUT       OUTPUT
```

# 11. Why Not One Policy Class?

A beginner might write:

```python
class Policy(BaseModel):

    id: int
    name: str
    description: str
    maturity: str
    premium: float
```

And use it everywhere. But now creation requires:

```json
{
    "id": 0,
    "name": "Jeevan Labh",
    ...
}
```

That's not a good API contract. The database owns the ID. Therefore:

```text
PolicyCreate
     |
     +-- Client → Server


PolicyResponse
     |
     +-- Server → Client
```

Different responsibilities deserve different models.


# 12. PUT vs PATCH

For update:

```python
class PolicyUpdate(PolicyCreate):
    pass
```

This is useful when `PUT` means:

> Replace/update the complete resource. But suppose we want to change only premium.

```http
PATCH /api/policies/1
```

Request:

```json
{
    "premium": 18000
}
```

Then we might define:

```python
class PolicyPatch(BaseModel):

    name: str | None = None
    description: str | None = None
    maturity: str | None = None
    premium: float | None = Field(default=None, gt=0)
```

This is a good example of why **API models are designed according to operation**.

```python
class PolicyCreate(BaseModel):
```

```python
policy = Policy(id=1, name=request.name, description=request.description, maturity=request.maturity, remium=request.premium)
```

### Mentor's final message

> **Don't create classes just because Python allows you to create classes.**
>
> Create classes because they represent a **responsibility, boundary, or concept** in your application.
>
> **Pydantic models protect the API boundary.**
>
> **Dataclasses can represent the application's data/domain objects.**
>
> Good architecture is not about writing more classes.
>
> **Good architecture is about giving each class a clear responsibility.**
