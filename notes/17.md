### 2. What Is Event-Driven Programming?

Event-driven programming is a programming paradigm in which the execution of application logic is triggered by events. An event represents something that has happened.

In TFLInsurance, examples include:

|Business Event         |               Meaning                 |
| --------------------  |-------------------------------------- |
|`CustomerRegistered`   |A new customer has registered          |
|`PolicyCreated`        |A new policy has been created          |
|`PremiumPaid`          |Customer has completed premium payment |
|`ClaimSubmitted`       |Customer has submitted a claim         |
|`ClaimApproved`        |Claims officer has approved a claim    |
|`ClaimRejected`        |Claim has been rejected                |
|`PolicyExpired`        |Policy has reached its expiry date     |

### Real-world analogy

Imagine a claims department. A customer submits a claim. The claims officer receives the information and begins processing it. The claims officer doesn't need to continuously ask the customer whether a claim has been submitted. The submission itself becomes an event that triggers the next activity.

Mentor's definition:

> An event is a signal that something has happened. An event handler is a function that responds to that event.

### 3. Procedural Programming vs Event-Driven Programming

#### A. Procedural Thinking

A beginner might write:

```
def process_claim():

    submit_claim()
    validate_claim()
    notify_customer()
    notify_claims_officer()
    update_audit_log()
    print("Claim submitted successfully")
```

Everything is controlled by one function.

#### Execution flow

```
              process_claim()
                    |
                    v
              submit_claim()
                    |
                    v
             validate_claim()
                    |
                    v
             notify_customer()
                    |
                    v
          notify_claims_officer()
                    |
                    v
             update_audit_log()
                    |
                    v
                   END
```

As the application grows, the function may become responsible for too many operations.


#### B. Event-Driven Thinking

Instead, we publish an event when a claim is submitted.

```
                 Customer
                    |
                    v
              Submit Claim
                    |
                    v
             ClaimSubmitted
                    |
                    v
            Event Dispatcher
                    |
          +---------+---------+
          |         |         |
          v         v         v
       Validate   Notify    Audit
        Claim    Customer   Logging
```

Each handler has its own responsibility. The claim submission process does not need to know every detail of the notification or audit implementation.

### 4. Four Fundamental Components of Event-Driven Programming

#### 1. Event

Something that happens in the business system.

Example: `ClaimSubmitted`

####  2. Event Source

The component that generates the event. Example: Claim API or Claim Service.

####  3. Event Handler

A function that responds to the event.

Example: `notify_claims_officer()`

#### 4. Event Dispatcher / Event Loop

Coordinates event delivery and execution of registered handlers.

Example: A custom Python event dispatcher or `asyncio` event loop.

### TFLInsurance event flow

```
       Claim Submission API
                |
                v
         ClaimSubmitted
                |
                v
        Event Dispatcher
                |
        +-------+-------+
        |       |       |
        v       v       v
     Handler Handler Handler
        |       |       |
        v       v       v
     Validate Notify  Audit
      Claim  Customer Log
```

### 5. Python Demonstration – Creating Our Own Event Dispatcher

Ravi Sir:

"Let's build our own event system using Python. No external framework is required."

We will implement three operations:

1. Subscribe to an event.
2. Publish an event.
3. Execute registered handlers.

## Step 1: Create EventDispatcher

Python

Run

```
class EventDispatcher:

    def __init__(self):
        self.handlers = {}

    def subscribe(self, event_name, handler):

        if event_name not in self.handlers:
            self.handlers[event_name] = []

        self.handlers[event_name].append(handler)

    def publish(self, event_name, data):

        print(f"\nEvent Published: {event_name}")

        for handler in self.handlers.get(event_name, []):
            handler(data)
```

#### Understanding the class

|Method       | Responsibility                                      |
| ----------- | --------------------------------------------        |
|`__init__()` | Initializes the event handler registry              |
|`subscribe()`| Registers a function for an event                   |
|`publish()`  | Announces an event and invokes its handlers         |

The dictionary stores event names and their registered functions.

For example:

Python

Run

```
{
    "ClaimSubmitted": [
        validate_claim,
        notify_customer,
        notify_claims_officer
    ]
}
```

### 6. TFLInsurance – Claim Submitted Event

Let's implement our first business event.

## Step 1: Define the event handlers

Python

Run

```
def validate_claim(data):

    print("Validating claim:", data["claim_id"])

    if data["amount"] <= 0:
        print("Invalid claim amount")
        return

    print("Claim validation completed")


def notify_customer(data):

    print("Sending claim acknowledgement to:",
          data["customer_email"])


def notify_claims_officer(data):

    print("Notifying claims officer about:",
          data["claim_id"])


def update_audit_log(data):

    print("Recording claim submission in audit log")
```

Each function handles one responsibility.

## Step 2: Register handlers

Python

Run

```
dispatcher = EventDispatcher()
dispatcher.subscribe("ClaimSubmitted", validate_claim)
dispatcher.subscribe("ClaimSubmitted", notify_customer)
dispatcher.subscribe("ClaimSubmitted", notify_claims_officer)
dispatcher.subscribe("ClaimSubmitted", update_audit_log)
```

## Step 3: Publish the event

Python

Run

```
claim = {
    "claim_id": "CLM1001",
    "customer_name": "Rahul",
    "customer_email": "rahul@example.com",
    "amount": 50000
}

dispatcher.publish("ClaimSubmitted", claim)
```

### 7. Python Callbacks – A Function Responding to a Business Operation

A callback is a function passed to another function so that it can be invoked later. Consider premium payment. After successful payment, we want to invoke a confirmation function.

Python

Run

```
def process_premium_payment(amount, callback):

    print("Processing premium payment:", amount)
    print("Payment successful!")
    callback(amount)


def payment_confirmation(amount):
    print("Premium payment confirmed:", amount)


process_premium_payment(25000, payment_confirmation)
```

### Expected output

```
Processing premium payment: 25000
Payment successful!

Premium payment confirmed: 25000
```

### Callback flow

```
       process_premium_payment()
                   |
                   v
           Process Payment
                   |
                   v
          Payment Successful
                   |
                   v
            Invoke Callback
                   |
                   v
          payment_confirmation()
```

### Mentor asks

"Why are we passing `payment_confirmation` without parentheses?"

Because we are passing the function reference.

Python

Run

```
payment_confirmation
```

Means function reference.

Python

Run

```
payment_confirmation(25000)
```

Means function invocation. Connection to event-driven programming: An event handler is commonly implemented as a callback registered with an event source or dispatcher.

### 8. Event-Driven Programming with Python asyncio

Now consider a real insurance application. Multiple customers may submit claims simultaneously. The application may need to:

* Call an external verification API.
* Retrieve policy details from a database.
* Send notifications.
* Wait for payment gateway responses.

These are I/O-oriented operations.

Python's `asyncio` library allows asynchronous tasks to suspend while waiting for I/O, allowing the event loop to run other ready tasks.

## Example: Processing Multiple Insurance Claims

Python

Run

```
import asyncio

async def process_claim(claim_id, delay):

    print(f"Started processing claim: {claim_id}")
    await asyncio.sleep(delay)
    print(f"Completed processing claim: {claim_id}")

async def main():

    await asyncio.gather(
        process_claim("CLM1001", 3),
        process_claim("CLM1002", 2),
        process_claim("CLM1003", 1)
    )


asyncio.run(main())
```

### Expected output

```
Started processing claim: CLM1001
Started processing claim: CLM1002
Started processing claim: CLM1003

Completed processing claim: CLM1003
Completed processing claim: CLM1002
Completed processing claim: CLM1001
```

The tasks overlap while waiting. `asyncio.sleep()` is a non-blocking wait. It suspends the current coroutine and allows the event loop to run other tasks.

### Event loop visualization

```
                 asyncio.run(main())
                         |
                         v
                  +-------------+
                  | Event Loop  |
                  +-------------+
                         |
             +-----------+-----------+
             |           |           |
             v           v           v
         Claim 1001  Claim 1002  Claim 1003
             |           |           |
             v           v           v
          Waiting     Waiting     Waiting
             |           |           |
             +-----------+-----------+
                         |
                         v
                 Resume Ready Tasks
                         |
                         v
                   Complete Tasks
```

Important distinction:

Event-driven programming describes how an application responds to events. Asynchronous programming describes how operations can suspend and resume without blocking the execution thread.

They are related, but not identical.

### 10. Real-World Event-Driven Architecture – Insurance Claim Processing

Let's now think like software architects. A customer submits a claim through the TFLInsurance portal.

The application publishes:

```
ClaimSubmitted
```

Different services can react to the event.

### Business architecture

```
                   Customer
                      |
                      v
                Submit Claim
                      |
                      v
                 Claim API
                      |
                      v
              ClaimSubmitted Event
                      |
                      v
               Event Broker
                      |
          +-----------+-----------+
          |           |           |
          v           v           v
     Validation   Notification   Audit
       Service      Service     Service
          |
          v
     Claim Review
          |
          v
     Claims Officer
          |
          v
     ClaimApproved
          |
          +-----------------------+
          |                       |
          v                       v
     Payment Service       Customer Notification
          |
          v
     Payment Processed
```

In a distributed system, the event broker could be RabbitMQ, Kafka, or a cloud messaging service. This architecture allows the claim service and its consumers to evolve independently.

### Important engineering considerations

* Retries: What happens if a notification service temporarily fails?
* Duplicate events: Can processing the same event twice cause duplicate payments?
* Event ordering: What if `ClaimApproved` is received before an earlier event?
* Eventual consistency: Different services may update their records at different times.
* Observability: How can we trace a claim across multiple services?

These are important topics when moving from a classroom event dispatcher to production event-driven architecture.
