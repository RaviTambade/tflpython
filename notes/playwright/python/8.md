# Lesson 8: Authentication, roles, isolation, and parallel execution

**Theme:** Verify who a user is, what that user may do, and whether concurrent tests remain independent.

## 1. Authentication and authorization

| Authentication | Authorization |
|---|---|
| Establishes who the user is | Determines what an authenticated user may do |
| Login, session, or token validation | Roles, scopes, policies, ownership |
| Often returns 401 when missing or invalid | Often returns 403 when access is denied |

Use the application's documented semantics: some applications return 404 instead of 403 to hide the existence of restricted resources.

## 2. JWT flow and security checks

```text
test client -> login endpoint -> credentials checked -> token/session issued
test client -> protected endpoint + credentials -> identity and permissions checked
```

Test the contract for valid credentials, invalid credentials, missing credentials, malformed/expired tokens, and each relevant authorization boundary. Never hard-code production credentials or print bearer tokens.

## 3. Verify authorized and denied requests

```python
from playwright.sync_api import APIRequestContext


def test_student_access_boundaries(student_api: APIRequestContext) -> None:
    own_profile = student_api.get("/api/student/profile")
    assert own_profile.status == 200

    mentor_area = student_api.get("/api/mentor/dashboard")
    assert mentor_area.status == 403
```

Add explicit unauthenticated and invalid-token tests with a separate request context that has no authorization header. Do not assume one request's status proves that every route is protected.

## 4. Role-based test matrix

| Identity | Resource | Expected result |
|---|---|---|
| Anonymous | Protected profile | 401 or documented sign-in redirect |
| Student | Own profile | 200 |
| Student | Mentor dashboard | 403 or documented denial |
| Mentor | Mentor dashboard | 200 |
| Admin | Admin function | 200 |

Add ownership tests (for example, one student cannot modify another student's assessment) when the application supports them. Verify both the allowed operation and the denied boundary.

## 5. Browser storage state

Playwright can save and load browser storage state for repeatable login setups. Treat the state file like a password: exclude it from Git, restrict access, rotate it, and avoid attaching it to publicly visible reports. Separate role state files where appropriate. API bearer tokens and browser cookies are not interchangeable; use the mechanism the application actually
implements.

## 6. Test isolation and data strategy

- Give each test unique data, such as a `uuid4()` suffix.
- Use a fresh browser context per test unless state sharing is intentional.
- Create data through supported test APIs or UI flows.
- Delete only data created by that test.
- Avoid shared mutable accounts and fixed names in parallel tests.
- Keep cleanup in fixture teardown or `finally`, and surface cleanup failures.
- Do not assume tests run in a particular order.

## 7. Parallel execution and useful commands

```bash
pytest
pytest -n 2
pytest -k "auth or login"
pytest --browser chromium
pytest --headed
pytest --tracing retain-on-failure
```

Use `pytest-xdist` for `-n`. Parallelism can expose shared-data bugs; it is not a substitute for isolating test resources. Start with one worker, establish a stable baseline, then increase concurrency.

## 8. Practical assignment and final checklist

Implement a role matrix for anonymous, student, mentor, and administrator identities. Verify login, an allowed operation, a forbidden operation, and data isolation for two users. Run the tests with more than one worker.

Before sharing results, confirm:

- The tests ran against a dedicated test environment.
- Expected statuses and role rules match the application's contract.
- Secrets, tokens, and saved browser state are not committed or exposed.
- Tests create and clean up their own data.
- Browser traces and reports are handled as potentially sensitive artifacts.
- Failures and skips are reported honestly.
