# Pytest Fixtures and Test Lifecycle

**Theme**: Reuse setup safely, manage dependencies intelligently, and ensure cleanup executes even when assertions fail.

## 1. Mentor's introduction – Why do we need fixtures?

Imagine we are testing an e-commerce application. We have 100 test cases:

- Login page testing
- Product page testing
- Shopping cart testing
- Order placement testing
- Payment testing
- Dashboard testing

Every test requires some preparation.

For example:

1. Start browser.
2. Open application.
3. Login if necessary.
4. Prepare test data.
5. Execute test.
6. Clean up test data.

Should we write this preparation code inside every test?  Absolutely not!  This creates duplication and makes the automation framework difficult to maintain. Pytest Fixture provides a mechanism to prepare, share and clean up resources used by test cases. Think of a fixture as a laboratory assistant who prepares the experiment before the student starts working and cleans the laboratory afterward.

## 2. Understand the test lifecycle

```
             Pytest Test Runner
                     |
                     v
              Discover Test Cases
                     |
                     v
              Resolve Fixtures
                     |
                     v
              Execute Setup Code
                     |
                     v
                Run Test Case
                     |
                     v
              Evaluate Assertions
                     |
                     v
               Test PASS / FAIL
                     |
                     v
              Execute Teardown
                     |
                     v
               Release Resources
                     |
                     v
              Generate Test Report
```

**The important observation**:Setup happens before the test. Teardown happens after the test. Even if an assertion fails, Pytest executes fixture teardown code after `yield`.

## 3. What is a Pytest fixture?

Consider this example:

```
import pytest@pytest.fixture

def message():    
       return "Welcome to Transflower"

def test_message(message):    
       assert message == "Welcome to Transflower"
```

Here:

- `@pytest.fixture` identifies a fixture.
- `message()` prepares a value.
- `test_message()` consumes the fixture.
- Pytest automatically injects the fixture into the test.

Notice that we never call `message()` ourselves. Pytest manages the dependency.

### Understand dependency injection

```
              Pytest Framework
                     |
                     v
               test_message()
                     |
                     v
               Needs message
                     |
                     v
               message fixture
                     |
                     v
            Returns prepared value
                     |
                     v
              Test executes
```

This is dependency injection at the test framework level.

## 4. First practical example – Home page fixture

File: `tests/conftest.py`

```
import pytest
from playwright.sync_api import Page

@pytest.fixture
def home_page(page: Page, base_url: str) -> Page:
    page.goto(base_url)
    return page
```

Test file: `tests/test_home.py`

```
from playwright.sync_api import Page
def test_home_has_navigation(home_page: Page) -> None:
    assert home_page.get_by_role("navigation").is_visible()
```

What happened?

1. Pytest identifies `home_page` as a required fixture.
2. It resolves the `page` fixture.
3. It resolves `base_url`.
4. It opens the application.
5. It injects the prepared page into the test.

Note: The navigation locator assumes the application exposes a navigation element with the appropriate accessible role.

## 5. Understand fixture scopes

Pytest supports five fixture scopes.

| Scope      | Lifetime               | Typical use                 |
| ---------- | ---------------------- | --------------------------- |
| `function` | Once per test function | Browser page, test data     |
| `class`    | Once per test class    | Shared class setup          |
| `module`   | Once per Python module | Module-level resources      |
| `package`  | Once per package       | Package-level configuration |
| `session`  | Once per test session  | Global configuration        |

Example:

```
@pytest.fixture(scope="session")

def application_name():    
       return "Transflower"
```

Another example:

```
@pytest.fixture(scope="function")
def test_product():    
       return {"name": "Keyboard","price": 1200}
```

### Visualize fixture scope

```
             Pytest Session
                   |
        +----------+----------+
        |                     |
        v                     v
     Module A              Module B
        |                     |
    Class A1              Class B1
        |                     |
    +---+---+             +---+---+
    |       |             |       |
  Test 1  Test 2        Test 3  Test 4
    |       |             |       |
    v       v             v       v
 Function Function     Function Function
 Fixture  Fixture      Fixture  Fixture
```

Mentor's recommendation: Use function scope by default for mutable test resources. Use broader scopes only when sharing is intentional and safe. For example, a browser page should normally not be shared between independent test functions.

## 6. Understand setup and teardown using `yield`

Now consider a practical requirement. We create an API request context before executing a test. After the test finishes, we must release the context. How do we do that?

Use `yield`.

```
from collections.abc import Iterator
import pytestfrom playwright.sync_api 
import (APIRequestContext,Playwright)

@pytest.fixturedef api(playwright: Playwright, base_url: str) -> Iterator[APIRequestContext]:    
       context = playwright.request.new_context(base_url=base_url)    
       # Setup    
       yield context    
       # Teardown    
       context.dispose()
```

### Understand the lifecycle

```
           api() Fixture
                 |
                 v
       Create API Request Context
                 |
                 v
               yield
                 |
                 v
        Execute Test Function
                 |
                 v
        Assertion PASS / FAIL
                 |
                 v
          Return to Fixture
                 |
                 v
          context.dispose()
                 |
                 v
          Resource Released
```

Why is this useful? Suppose the test fails at this statement:

```
assert response.status == 200
```

The teardown code after `yield` still executes. This prevents unnecessary resource leaks. For resources requiring several cleanup operations, use `try/finally` and ensure cleanup errors are reported rather than silently ignored.

## 7. Understand fixture dependencies

A fixture can depend on another fixture.

Consider:

```
@pytest.fixture
def home_page(page, base_url):
       page.goto(base_url)    
       return page
```

Here:

- `home_page` depends on `page`.
- `home_page` also depends on `base_url`.
- Pytest resolves both dependencies automatically.

The dependency relationship looks like this:

```
                 Pytest
                   |
                   v
                home_page
                   |
             +-----+-----+
             |           |
             v           v
           page       base_url
             |           |
             v           v
          Browser     Environment
             |           |
             +-----+-----+
                   |
                   v
             Prepared Page
                   |
                   v
                Test Case
```

### Important scope rule

A broader-scoped fixture cannot depend on a narrower-scoped fixture.

For example:

```
@pytest.fixture(scope="session")

def browser_page(page):    
       return page
```

This is invalid because `page` is normally function-scoped, while `browser_page` is session-scoped.

Remember:

A session-scoped object cannot depend on a function-scoped object. Pytest reports a `ScopeMismatch` error in this situation.

## 8. Page Object Model + Fixtures

In Lesson 02, we introduced Page Object Model. Now let's integrate it with Pytest fixtures. Our objective is to create a reusable `LoginPage` fixture.

File: `pages/login_page.py`

```
from playwright.sync_api import Page

class LoginPage:

    def __init__(self, page: Page) -> None:
        self.page = page

    def open(self, base_url: str) -> None:
        self.page.goto(f"{base_url}/Account/Login")

    def sign_in(self, username: str, password: str) -> None:
        self.page.get_by_label("Username").fill(username)
        self.page.get_by_label("Password").fill(password)
        self.page.get_by_role("button",name="Sign in").click()
```

File: `tests/conftest.py`

```

import pytest

from playwright.sync_api import Page
from pages.login_page import LoginPage


@pytest.fixture
def login_page(page: Page) -> LoginPage:
    return LoginPage(page)
```

Now consume the fixture.

File: `tests/test_login.py`

```
from playwright.sync_api import expect
from pages.login_page import LoginPage


def test_login_form_is_ready(login_page: LoginPage, base_url: str) -> None:

    login_page.open(base_url)
    expect(login_page.page.get_by_label("Username")).to_be_editable()

```
What have we achieved?

- Page creation is managed by Playwright.
- LoginPage creation is managed by Pytest.
- Test execution is managed by Pytest.
- Browser cleanup is managed by pytest-playwright.

This is a clean separation of responsibilities.

## 9. Create an authenticated_page fixture

This is our main practical exercise. Suppose we have 50 dashboard test cases. Should every test independently implement login? No. We can create an `authenticated_page` fixture that logs in once for each test that needs it.

File: `tests/conftest.py`

```
import os
import pytest

from playwright.sync_api import Page, expect
from pages.login_page import LoginPage

@pytest.fixture
def authenticated_page(page: Page,base_url: str) -> Page:

    # Step 1: Read credentials from environment variables

    username = os.environ.get("TEST_USERNAME")
    password = os.environ.get("TEST_PASSWORD")

    # Step 2: Validate credentials
    if not username or not password:
        pytest.fail("Set TEST_USERNAME and TEST_PASSWORD")

    # Step 3: Create Login Page object
    login = LoginPage(page)

    # Step 4: Navigate to application
    login.open(base_url)

    # Step 5: Perform login
    login.sign_in(username, password)

    # Step 6: Verify successful authentication
    expect(page).to_have_url(f"{base_url}/Dashboard")

    # Step 7: Provide authenticated page to test
    return page
```

Notice the important detail: We verify successful login inside the fixture before returning the authenticated page. If login fails, the dependent test must not continue as though authentication succeeded.

### Consume the fixture

File: `tests/test_dashboard.py`

```

from playwright.sync_api import Page, expect

def test_dashboard_is_visible(authenticated_page: Page) -> None:

    # Step 1: Locate Dashboard heading
    dashboard_heading = authenticated_page.get_by_role("heading", name="Dashboard")

    # Step 2: Verify Dashboard heading is visible
    expect(dashboard_heading).to_be_visible()

```

### Understand the execution

```
            test_dashboard_is_visible()
                       |
                       v
             authenticated_page
                       |
                       v
                 Read Secrets
                       |
                       v
                 Open Login
                       |
                       v
                Enter Credentials
                       |
                       v
                 Click Sign in
                       |
                       v
              Verify Dashboard URL
                       |
                       v
               Return Page Object
                       |
                       v
               Execute Dashboard Test
                       |
                       v
                Verify Dashboard
                       |
                       v
                    PASS
```

Each test using this fixture gets its own login workflow and isolated page.
**Security note**: Use a dedicated test account, store credentials in secure environment configuration, and avoid exposing them in logs or reports.

## 10. Fixture teardown and resource management

Consider an API test that creates a product.

```
import pytest

@pytest.fixture
def product(api):

    # Step 1: Create a temporary product

    response = api.post("/api/products",
                     data={
                     "name": "Temporary Keyboard",
                     "price": 1200,
                     "quantity": 2
                     }
    )

    # Step 2: Verify product creation
    assert response.status == 201

    # Step 3: Extract the generated product ID
    product_id = response.json()["id"]

    # Step 4: Provide product ID to the test
    yield product_id

    # Step 5: Cleanup - Delete temporary product
    deleted = api.delete(f"/api/products/{product_id}"
    )

    # Step 6: Verify successful deletion
    assert deleted.status in (200, 204)

```

Test:

```
def test_product_exists(api, product):

    # Step 1: Send GET request to retrieve product
    response = api.get(f"/api/products/{product}")

    # Step 2: Verify successful HTTP response
    assert response.status == 200
```

Here, the fixture:

1. Creates the product.
2. Passes its ID to the test.
3. Allows the test to execute.
4. Deletes the product afterward.

If the test assertion fails, the fixture teardown still runs. For a more robust fixture, track successful creation and protect cleanup with `try/finally`. Also remember that cleanup can fail independently; Pytest should report that failure.

## 11. Pytest hooks vs fixtures

Students often confuse fixtures and hooks. They serve different purposes.

| Fixture                     | Hook                                               |
| --------------------------- | -------------------------------------------------- |
| Prepares test dependencies  | Extends Pytest runner behavior                     |
| Provides resources to tests | Responds to test lifecycle events                  |
| Handles setup and teardown  | Handles reporting, collection and execution events |
| Explicit dependencies       | Framework-level integration                        |

Example:

```
import pytest


@pytest.fixture
def database_connection():

    # Step 1: Establish database connection
    connection = create_connection()

    # Step 2: Provide connection to the test
    yield connection

    # Step 3: Cleanup - Close database connection
    connection.close()
```

This is an appropriate use of a fixture. A hook is useful when we want to capture information about test execution across the entire test suite.

### Example: Capture screenshots when a test fails

In `conftest.py`:

```
import pytest

@pytest.hookimpl(hookwrapper=True)
def pytest_runtest_makereport(item,call):

    # Step 1: Execute pytest's reporting process
    outcome = yield

    # Step 2: Get the test execution report
    report = outcome.get_result()

    # Step 3: Check whether the actual test failed
    if report.when == "call" and report.failed:

        # Step 4: Get Playwright page fixture
        page = item.funcargs.get("page")

        # Step 5: Capture screenshot if page exists
        if page:
            page.screenshot(path=f"screenshots/{item.name}.png",full_page=True)
```

This illustrates the lifecycle hook concept. For a production implementation, create the screenshot directory, use unique filenames, and handle cases where the browser page has already closed. You can also use the Playwright Pytest plugin's built-in failure screenshot and tracing options.

**Mentor's  advice**: Use fixtures for normal test setup and teardown. Use hooks for cross-cutting test-runner behavior.

## 12. Debugging and executing tests

Some useful Pytest commands:

| Command                              | Purpose                                   |
| ------------------------------------ | ----------------------------------------- |
| `pytest -v`                          | Verbose test execution                    |
| `pytest -k login`                    | Run tests matching login                  |
| `pytest --headed`                    | Display browser during execution          |
| `pytest --tracing retain-on-failure` | Retain Playwright traces for failed tests |
| `pytest -s`                          | Display print statements                  |
| `pytest -x`                          | Stop after first failure                  |
| `pytest --tb=short`                  | Short traceback                           |

Example:

```
pytest -v -k login --headed
```

To generate an HTML report, install:

```
pip install pytest-html
```

Then execute:

```
pytest -v --html=reports/report.html --self-contained-html
```
