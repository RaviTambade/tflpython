## Build Your First Playwright + Python Browser Suite

Theme: Automate a complete login journey using pytest and a real browser.

## 1. Mentor introduces the problem

**Mentor**: Imagine that you have joined a software development team as an SDET. Your organization has developed an ASP.NET Core MVC application. The development team has implemented authentication functionality. The application contains:

- Login page
- Username and password fields
- Sign-in button
- Dashboard
- Authentication validation
- Access-control mechanism

The development team says:

"Our login functionality is ready. Please test it."

**Question**: How will you verify that login functionality actually works?

**Student**: We can manually open the browser, enter credentials and verify the dashboard.

**Mentor**: Correct. But what happens when we need to execute these tests 100 times, across different browsers and application versions?

**Student**: We should automate the testing process.

**Mentor**: Exactly! This is where Python, pytest and Playwright come together.

```

```

```

```

### Step 3: Install dependencies

```
python -m pip install pytest pytest-playwright

```

### Step 4: Create project structure

```
playwright-python/
│
├── pages/
│   └── login_page.py
│
├── tests/
│   ├── conftest.py
│   └── test_login.py
│
├── pytest.ini
├── requirements.txt
└── .gitignore
```

**Mentor**: Why are we creating separate folders?

Because test scenarios and page interaction logic have different responsibilities.

- `pages/` contains page objects.
- `tests/` contains test cases.
- `conftest.py` contains reusable fixtures.
- `pytest.ini` contains test configuration.

## 4. Configure pytest

Create `pytest.ini`.

```
[pytest]

testpaths = tests

addopts = -ra
```

This configuration tells pytest where to discover test cases. Create `requirements.txt`.

```
pytest
pytest-playwright
```

Create `.gitignore`.

```
venv/
__pycache__/
.pytest_cache/
test-results/
playwright-report/
*.pyc
.env
```

Never commit real credentials, authentication tokens or sensitive test artifacts.

## 5. Configure the application URL using fixtures

Create `tests/conftest.py`.

```
import os
import pytest

@pytest.fixture(scope="session")
def base_url() -> str:

    value = os.environ.get("BASE_URL")

    if not value:
        pytest.fail("Set BASE_URL to the test application's URL" )

    return value.rstrip("/")
```

The `page` fixture is automatically provided by pytest-playwright.

**Student**: To reuse setup and teardown operations across multiple test cases.

**Mentor**: Correct. Fixtures help us avoid duplicate initialization code.

## 6. Write your first browser test

Create `tests/test_login.py`.

```
from playwright.sync_api import Page, expect


def test_login_page_is_available(page: Page, base_url: str) -> None:

    page.goto(f"{base_url}/Account/Login")
    expect(page).to_have_title("Sign in")
    expect(page.get_by_label("Username")).to_be_visible()
    expect(page.get_by_label("Password")).to_be_visible()
    expect(page.get_by_role("button",name="Sign in")).to_be_enabled()
```

### Understand the Playwright commands

| Command           | Purpose                       |
| ----------------- | ----------------------------- |
| `page.goto()`     | Opens application URL         |
| `get_by_label()`  | Finds form controls           |
| `get_by_role()`   | Finds accessible UI elements  |
| `to_have_title()` | Verifies page title           |
| `to_be_visible()` | Verifies element visibility   |
| `to_be_enabled()` | Verifies control availability |

### Locator preference

1. `get_by_role()` – accessible roles and names.
2. `get_by_label()` – form controls.
3. `get_by_placeholder()` – meaningful placeholders.
4. `get_by_test_id()` – stable test identifiers.
5. CSS/XPath – when other locators are unsuitable.

Mentor tip: Prefer locators based on how users interact with the application rather than its internal HTML structure.

## 7. Implement Page Object Model

Now let's make our automation reusable.

Create `pages/login_page.py`.

```
from playwright.sync_api import Page


class LoginPage:

    def __init__(self, page: Page) -> None:
        self.page = page
        self.username = page.get_by_label("Username")
        self.password = page.get_by_label("Password")
        self.sign_in_button = page.get_by_role("button",name="Sign in")

    def open(self, base_url: str) -> None:
        self.page.goto(f"{base_url}/Account/Login")

    def submit(self,username: str,password: str) -> None:
        self.username.fill(username)
        self.password.fill(password)
        self.sign_in_button.click()
```

### Understand the relationship

```
         test_login.py
               |
               v
          LoginPage
               |
       +-------+-------+
       |       |       |
       v       v       v
    Username Password Button
       |       |       |
       +-------+-------+
               |
               v
         Playwright Page
               |
               v
          Web Browser
```

The Page Object Model centralizes page interactions, while test cases describe expected business behavior.

## 8. Test successful and failed login

### Scenario A: Valid credentials

```
import os
import pytest

from playwright.sync_api import Page, expect
from pages.login_page import LoginPage


def test_valid_user_reaches_dashboard(
    page: Page,
    base_url: str
) -> None:

    username = os.environ.get("TEST_USERNAME")
    password = os.environ.get("TEST_PASSWORD")

    if not username or not password:
        pytest.fail("Set TEST_USERNAME and TEST_PASSWORD")

    login = LoginPage(page)
    login.open(base_url)
    login.submit(username, password)

    expect(page).to_have_url(f"{base_url}/Dashboard")
    expect(page.get_by_role("heading",name="Dashboard")).to_be_visible()
```

### Scenario B: Invalid credentials

```
def test_invalid_password_shows_error(page: Page,base_url: str) -> None:

    login = LoginPage(page)
    login.open(base_url)
    login.submit("invalid-user@example.test", "invalid-password")
    expect(page.get_by_role("alert")).to_contain_text("Invalid credentials")
```

The test account must be a dedicated, non-production account. Store its credentials in environment variables or a secure CI secret store.

## 9. Test authentication and authorization

**Authentication** answers:"Who are you?"

**Authorization** answers:"What are you allowed to access?"

Suppose an unauthenticated user attempts to access the dashboard directly. The application should redirect that user to the login page.

```

       v       v

```

### Test protected page

```
def test_dashboard_requires_login(page: Page, base_url: str) -> None:

    page.goto(f"{base_url}/Dashboard")
    expect(page).to_have_url(f"{base_url}/Account/Login")
    expect(page.get_by_label("Username")).to_be_visible()
```

The expected route depends on the actual application's authentication configuration.

## 10. Run and debug your test suite

### Execute all tests

```
pytest
```

### Verbose execution

```
pytest -v
```

### Execute selected tests

```
pytest -k login -v
```

### Open the browser

```
pytest --headed
```

### Slow down browser execution

```
pytest --headed --slowmo 250
```

### Capture traces on failure

```
pytest --tracing retain-on-failure
```

### Generate HTML report

Install:

```
pip install pytest-html
```

Execute:

```
pytest --html=report.html --self-contained-html
```

Reports and traces can contain sensitive application information. Keep them out of source control and protect them in CI.

from playwright.sync_api import Page


class LoginPage:

## 13. Ravi Sir's classroom discussion

**Mentor**: What is the difference between manually testing a login page and automating a login page?

**Student**: Manual testing requires a person to perform the steps. Automation executes predefined test scenarios repeatedly.

**Mentor**: Good. Does successful login prove that the entire application is working?

**Student**: No, Sir. We also need to verify dashboard behavior, authorization, session handling and other business workflows.

**Mentor**: Excellent! One more question. If we change ASP.NET Core MVC to React, should our entire automation suite change?

**Student**: Not necessarily. We should update the page interactions and locators where required, while preserving business test scenarios.

**Mentor**: Exactly! A good SDET does not merely test screens. A good SDET verifies business behavior through complete user journeys.
