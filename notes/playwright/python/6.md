# Lesson 6: Database verification with Python, Playwright, and MySQL

**Theme:** Verify that user-visible or API operations persist the intended
data, using a safe test database.

## 1. Testing boundary

Prefer to create, update, and delete business data through the application's UI or API. A direct database connection can verify persisted state and support controlled cleanup; it should not replace tests of application behavior or business rules.

```text
pytest -> Playwright browser/API -> application -> service/repository -> MySQL
                                                        |
                                      test DB read-back and cleanup
```

Never point automated write tests at production. Use a dedicated test schema and a least-privilege test account.

## 2. Example schema

```sql
CREATE TABLE products (
    product_id INT PRIMARY KEY AUTO_INCREMENT,
    product_name VARCHAR(100) NOT NULL,
    price DECIMAL(10, 2) NOT NULL,
    quantity INT NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

Keep schema creation in controlled migrations or test-environment setup; tests should not assume arbitrary pre-existing rows.

## 3. Install a Python MySQL driver

For example, install `mysql-connector-python` in the project's virtual environment. Put connection configuration in environment variables or a secret manager, and add local secret files to `.gitignore`.

```text
DB_HOST=127.0.0.1
DB_PORT=3306
DB_USER=automation_test
DB_PASSWORD=<provided securely>
DB_NAME=tfl_playwright_test
```

Do not commit passwords or print environment values in test failures.

## 4. Create a connection fixture

```python
from collections.abc import Iterator
import os

import mysql.connector
import pytest
from mysql.connector.connection import MySQLConnection


@pytest.fixture
def db_connection() -> Iterator[MySQLConnection]:
    required = ("DB_HOST", "DB_USER", "DB_PASSWORD", "DB_NAME")
    missing = [key for key in required if not os.environ.get(key)]
    if missing:
        pytest.fail(f"Missing database configuration: {', '.join(missing)}")

    connection = mysql.connector.connect(
        host=os.environ["DB_HOST"],
        port=int(os.environ.get("DB_PORT", "3306")),
        user=os.environ["DB_USER"],
        password=os.environ["DB_PASSWORD"],
        database=os.environ["DB_NAME"],
    )
    yield connection
    connection.close()
```

Do not silently skip a required integration test because the database is unavailable. If a database tier is optional in a local workflow, mark it explicitly and report the skip reason.

## 5. Create through the API, verify through the database

Use parameterized SQL; never interpolate untrusted values into query strings. The placeholder syntax below is for MySQL Connector/Python.

```python
from uuid import uuid4

from playwright.sync_api import APIRequestContext


def test_created_product_is_persisted(api: APIRequestContext, db_connection):
    marker = f"pw-{uuid4().hex}"
    cursor = db_connection.cursor(dictionary=True)
    product_id = None

    try:
        response = api.post( "/api/products", data={"name": marker, "price": 19.95, "quantity": 2}, )
        assert response.status == 201
        product_id = response.json()["id"]

        cursor.execute( "SELECT product_name, quantity FROM products WHERE product_id = %s", (product_id,),)
        row = cursor.fetchone()
        assert row is not None
        assert row["product_name"] == marker
        assert row["quantity"] == 2
    finally:
        if product_id is not None:
            cursor.execute(
                "DELETE FROM products WHERE product_id = %s",
                (product_id,),
            )
            db_connection.commit()
        cursor.close()
```

Adjust identifiers, status codes, and column names to the application's contract. The example assumes the test user's database permissions allow cleanup in this test schema.

## 6. Test data and concurrency

Generate a unique marker per test (for example with `uuid4`), associate created rows with that marker, and delete only rows created by the test. Avoid global truncation or cleanup that could affect another worker's data.

Use transactions only when application behavior and connection boundaries make rollback reliable. An app server normally commits through its own connection, so rolling back the test's separate connection may not undo the application's write.
