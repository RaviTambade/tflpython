# Database Verification with Python, Playwright and MySQL

**Theme**: Don't just verify what the user sees. Verify what the application actually saves.

**Mentor**: Suppose a user creates a product using an e-commerce application. The application displays:

```
Product Created Successfully!

Product Name : Wireless Keyboard
Price        : 1200.00
Quantity     : 5
```

- How do we know that the product was actually saved in the database?
- Can we trust the success message displayed by the UI?

Not necessarily! The application might display a success message even when the database operation fails, or it might save incorrect values. As automation engineers, we need to verify the complete data flow.

##  Database Verification with Python, Playwright and MySQL

**Theme:** Verify that user-visible or API operations persist the intended data using a safe test database.

## 2. Testing boundary: Understanding the architecture

A testing engineer should understand where to perform testing and where to perform verification.

```
        SDET / Automation Engineer
                   |
                   v
             pytest Runner
                   |
                   v
          Playwright Browser/API
                   |
                   v
            Application Layer
                   |
                   v
             Business Service
                   |
                   v
             Repository Layer
                   |
                   v
               MySQL DB
                   |
                   v
          Persisted Business Data
```

The automation engineer performs two important activities:

**Activity 1: Application interaction**

Create, update and delete business data through the application UI or API.

**Activity 2: Database verification**

Connect directly to the test database and verify the persisted records.

Remember:

- UI/API testing verifies application behavior.
- Database testing verifies persistence.
- Business rules must be tested through the application.
- Database access should not bypass application authorization or business logic.

**Security rule:** Never execute automated write tests against production databases. Use a dedicated test schema and a least-privilege test account.

## 6. Create a reusable database fixture

**conftest.py**

```
from collections.abc import Iterator
import os

import mysql.connector
import pytest

from mysql.connector.connection import MySQLConnection


@pytest.fixture
def db_connection() -> Iterator[MySQLConnection]:

    required = ("DB_HOST", "DB_USER", "DB_PASSWORD","DB_NAME")

    missing = [
        key for key in required
        if not os.environ.get(key)
    ]

    if missing:
        pytest.fail(f"Missing database configuration: {', '.join(missing)}")

    connection = mysql.connector.connect(
                    host=os.environ["DB_HOST"],
                    port=int(os.environ.get("DB_PORT", "3306")),
                    user=os.environ["DB_USER"],
                    password=os.environ["DB_PASSWORD"],
                    database=os.environ["DB_NAME"],
    )

    try:
        yield connection
    finally:
        connection.close()
```

### Understanding the fixture

- `mysql.connector.connect()` establishes the database connection.
- `yield` provides the connection to the test.
- The test executes its database operations.
- The `finally` block closes the connection even if the test fails.

This is an example of resource lifecycle management.

## 7. Create a product through API and verify through MySQL

This is the most important practical exercise.

**test_products.py**

```
from uuid import uuid4

from playwright.sync_api import APIRequestContext


def test_created_product_is_persisted(api: APIRequestContext,db_connection):

    marker = f"pw-{uuid4().hex}"
    cursor = db_connection.cursor(dictionary=True)
    product_id = None

    try:
        response = api.post("/api/products",
            data={
                "name": marker,
                "price": 19.95,
                "quantity": 2
            }
        )

        assert response.status == 201

        product_id = response.json()["id"]

        cursor.execute(
            """
            SELECT product_name, quantity
            FROM products
            WHERE product_id = %s
            """,
            (product_id,)
        )

        row = cursor.fetchone()

        assert row is not None
        assert row["product_name"] == marker
        assert row["quantity"] == 2

    finally:

        if product_id is not None:
            cursor.execute(
                """
                DELETE FROM products
                WHERE product_id = %s
                """,
                (product_id,)
            )

            db_connection.commit()

        cursor.close()
```

### Understand the execution sequence

**Step 1: Generate unique test data**

```
marker = f"pw-{uuid4().hex}"
```

Every test execution generates a unique product name.

**Step 2: Create product through API**

```
response = api.post("/api/products",
    data={
        "name": marker,
        "price": 19.95,
        "quantity": 2
    }
)
```

**Step 3: Verify API response**

```
assert response.status == 201
```

**Step 4: Read product ID**

```
product_id = response.json()["id"]
```

**Step 5: Query MySQL**

```
cursor.execute("SELECT product_name, quantity FROM products WHERE product_id = %s", (product_id,))
```

Notice the `%s` placeholder.

This is parameterized SQL. Never construct SQL queries by concatenating untrusted input.

**Step 6: Verify persisted values**

```
assert row["product_name"] == marker
assert row["quantity"] == 2
```

**Step 7: Cleanup**

```
DELETE FROM products WHERE product_id = %s
```

We delete only the record created by this test.

## 9. Test data management and concurrency

Professional automation frameworks must be careful about test data.

Follow these principles:

1. Generate unique test data for every execution.
2. Use dedicated test schemas.
3. Delete only records created by the current test.
4. Never use global `TRUNCATE TABLE` cleanup.
5. Avoid shared mutable test accounts during parallel execution.
6. Use transactions only when application and database connection boundaries make rollback reliable.

**Remember**: Your application server generally uses its own database connection and commits its writes independently. Rolling back the automation test's separate connection will not normally undo those writes.

## Mentor's closing thought

**Testing is not complete when the application displays a success message. Testing is complete when the expected business outcome is verified at the appropriate boundaries.**

A good SDET understands three things:

1. What the user does.
2. What the application processes.
3. What the database persists.

**Remember: UI tells us what happened from the user's perspective. API tells us what the application returned. Database tells us what was persisted.**

## Mentor's additional teaching point

Three levels of verification

- **UI verification** --> Did the user see the expected result?

- **API verification** --> Did the application return the correct response?

- **Database verification** -->Was the intended data actually persisted?
