# API Testing with Playwright for Python

**Theme**: Test service contracts directly, then combine API setup with UI verification wherever it adds value.

## 1. Mentor's introduction: Why API testing?

Imagine we are developing an e-commerce application. A customer opens the browser, visits the Products page, searches for a keyboard and adds it to the shopping cart. What happens behind the scenes? The browser communicates with backend services through HTTP APIs.

```
                 Customer
                    |
                    v
               Web Browser
                    |
                    v
             React / Angular UI
                    |
                    v
                HTTP APIs
                    |
          +---------+---------+
          |         |         |
          v         v         v
       Product    Cart      Order
       Service   Service   Service
          |         |         |
          +---------+---------+
                    |
                    v
               MySQL Database
```

Now, suppose the Products page displays incorrect product information. Where is the problem?

- Is the browser rendering incorrectly?
- Is the API returning incorrect JSON?
- Is the backend business logic incorrect?
- Is the database returning incorrect records?

This is why SDETs need both UI testing and API testing. 
**Mentor's principle**: Test each architectural layer independently before testing the complete business workflow.

## 2. UI testing vs API testing

| Browser testing                            | API testing                       |
| ------------------------------------------ | --------------------------------- |
| Exercises rendered UI and browser behavior | Exercises HTTP contracts          |
| Uses locators and navigation               | Uses routes, headers and payloads |
| Usually slower                             | Usually faster                    |
| Validates user-visible behavior            | Validates service behavior        |
| Tests browser interactions                 | Tests request/response behavior   |
| Playwright Page                            | Playwright APIRequestContext      |

Both are necessary. API tests do not replace browser tests.

## 3. Understand HTTP methods

An API exposes operations on resources. Consider a Product resource.

| HTTP method | Purpose          | Example             |
| ----------- | ---------------- | ------------------- |
| GET         | Read resource    | `/api/products`     |
| POST        | Create resource  | `/api/products`     |
| PUT         | Replace resource | `/api/products/101` |
| PATCH       | Partially update | `/api/products/101` |
| DELETE      | Remove resource  | `/api/products/101` |

Think of an API as a service counter.

- GET: Show me a product.
- POST: Register a new product.
- PUT: Replace product information.
- PATCH: Change selected product information.
- DELETE: Remove a product.

## 5. Create an API context fixture

In browser testing, Pytest provides a `page` fixture. For API testing, Playwright provides `APIRequestContext`. We will create a reusable fixture that reads the API base URL from environment configuration.

File: `tests/conftest.py`

```
from collections.abc import Iterator
import os
import pytest
from playwright.sync_api import (APIRequestContext,Playwright)

@pytest.fixture
def api(playwright: Playwright) -> Iterator[APIRequestContext]:
    base_url = os.environ.get("API_BASE_URL")

    if not base_url:
        pytest.fail("Set API_BASE_URL to the test API URL")

    context = playwright.request.new_context(base_url=base_url.rstrip("/"))

    yield context
    context.dispose()
```

### Understand the fixture

| Statement       | Responsibility                          |
| --------------- | --------------------------------------- |
| `playwright`    | Provides Playwright API access          |
| `new_context()` | Creates an isolated API request context |
| `base_url`      | Configures the API server address       |
| `yield context` | Makes the context available to tests    |
| `dispose()`     | Releases API context resources          |

Why function scope? Every test receives a fresh API context. This helps prevent cookies and request state from leaking between tests.

## 7. First API test – Read products

**Business requirement**: The product service should return a list of products.

File: `tests/test_products_api.py`

```
from playwright.sync_api import APIRequestContext

def test_list_products(api: APIRequestContext) -> None:
    response = api.get("/api/products")
    assert response.status == 200
    products = response.json()
    assert isinstance(products, list)
```

Expected response:

```
[
    {"id": 101,"name": "Keyboard","price": 1200,"quantity": 10},
    {"id": 102,"name": "Mouse","price": 600,"quantity": 20}
]
```

The test checks:

1. Did the server respond successfully?
2. Is the response a JSON list?
3. Does the service return the expected resource structure?

We can extend the assertions:

```
for product in products:
    assert "id" in product
    assert "name" in product
    assert "price" in product
    assert "quantity" in product
```

## 8. Second API test – Create and read a product

Now we will test a complete resource lifecycle. Business requirement: An authorized client should be able to register a new product and retrieve it using its generated ID.

```
from playwright.sync_api import APIRequestContext


def test_create_then_read_product(api: APIRequestContext) -> None:

    payload = {"name": "Test Keyboard", "price": 1200, "quantity": 3 }
    created = api.post("/api/products", data=payload )
    assert created.status in (200, 201)
    product = created.json()
    product_id = product["id"]

    try:
        assert product["name"] == payload["name"]
        fetched = api.get(f"/api/products/{product_id}")
        assert fetched.status == 200
        assert (fetched.json()["name"]== payload["name"])

    finally:
        deleted = api.delete(f"/api/products/{product_id}")
        assert deleted.status in (200, 204)
```

### Understand the execution flow

```
             Create Product
                   |
                   v
             POST /products
                   |
                   v
             HTTP 201 Created
                   |
                   v
             Read Product ID
                   |
                   v
             GET /products/{id}
                   |
                   v
             HTTP 200 OK
                   |
                   v
          Validate Product Details
                   |
                   v
             DELETE /products/{id}
                   |
                   v
             Cleanup Test Data
```

Important: The accepted status codes and JSON property names must match your actual API contract. If creation fails, cleanup should not attempt to delete a nonexistent resource. A production-quality fixture can track successful creation and perform teardown only when an ID has been obtained.

## 9. Third API test – Update and delete

Business requirement: The product service should allow modification and removal of an existing product.

```
def test_update_and_delete_product(api: APIRequestContext) -> None:

    created = api.post("/api/products",
        data={
            "name": "Temporary Product",
            "price": 10,
            "quantity": 1
        }
    )

    assert created.status == 201

    product_id = created.json()["id"]

    try:
        updated = api.put(f"/api/products/{product_id}",
            data={
                "name": "Updated Product",
                "price": 12,
                "quantity": 2
            }
        )

        assert updated.status == 200
        assert (updated.json()["name"] == "Updated Product")
        fetched = api.get(f"/api/products/{product_id}")

        assert fetched.status == 200
        assert (fetched.json()["price"] == 12)

    finally:
        deleted = api.delete(f"/api/products/{product_id}")

        assert deleted.status in (200, 204)
```

This test verifies three important operations:

- Create a resource.
- Update a resource.
- Delete a resource.

It also verifies that the updated values can be read back. For reliable parallel execution, generate unique test data and use an isolated test database or a dedicated test tenant. Do not let multiple test workers modify the same records.

## 10. Understand CRUD testing

| Operation      | HTTP method | Expected verification     |
| -------------- | ----------- | ------------------------- |
| Create         | POST        | Resource created          |
| Read           | GET         | Correct resource returned |
| Update         | PUT         | Updated resource returned |
| Partial update | PATCH       | Selected fields changed   |
| Delete         | DELETE      | Resource removed          |

Core SDET Skill

CRUD testing is one of the most frequently used techniques in API automation.

## 11. API authentication and negative testing

A good SDET must also test what happens when API requests are unauthorized. Consider a protected endpoint:

```
GET /api/orders
```

It should not expose confidential customer orders to anonymous users.

Example:

```
def test_unauthorized_request(api: APIRequestContext) -> None:

    response = api.get("/api/orders")
    assert response.status in (401, 403)
```

The exact expected status depends on the API security contract.

Other important negative scenarios:

| Test case                    | Expected behavior         |
| ---------------------------- | ------------------------- |
| Missing authentication token | 401 or specified response |
| Invalid token                | Authentication rejected   |
| Expired token                | Reauthentication required |
| Invalid product ID           | 400 or 404, as specified  |
| Missing product name         | Validation error          |
| Negative product price       | Validation error          |
| Unauthorized delete          | 403 or specified response |

For token-based authentication, Playwright supports request headers:

```
context = playwright.request.new_context(base_url=base_url,extra_http_headers={"Authorization": f"Bearer {token}"})
```

Read tokens from secure environment configuration. Never print credentials or tokens in test reports.

## 12. Combining API testing with UI testing

This is where things become interesting. Suppose we want to test whether a product appears correctly on the Products page. 
One approach:

1. Open the browser.
2. Navigate to Products.
3. Click Add Product.
4. Fill the form.
5. Submit.
6. Verify the product appears.

But this involves several UI operations just to create test data. An alternative is to create the product using the API and then verify it through the browser.

```
             Pytest Test
                  |
                  v
          Create Product via API
                  |
                  v
           POST /api/products
                  |
                  v
           Product Created
                  |
                  v
          Open Browser Page
                  |
                  v
           Navigate to Products
                  |
                  v
          Search for Test Product
                  |
                  v
          Verify Product Visible
                  |
                  v
               TEST PASS
```

Example:

```
from playwright.sync_api import Page, APIRequestContext, expect


def test_api_created_product_is_visible(page: Page,api: APIRequestContext,base_url: str) -> None:

    payload = {
        "name": "API Test Keyboard",
        "price": 1200,
        "quantity": 3
    }

    created = api.post("/api/products",data=payload)
    assert created.status == 201
    product_id = created.json()["id"]

    try:
        page.goto(f"{base_url}/Products")
        expect(page.get_by_text("API Test Keyboard")).to_be_visible()

    finally:
        deleted = api.delete(f"/api/products/{product_id}")
        assert deleted.status in (200, 204)
```

This example assumes the UI and API use the same test environment and database, and that the Products page displays newly created products. 

**Mentor observation**: API creates the test data; Playwright verifies the user experience.

This is a powerful combination for enterprise test automation.

**Ravi Sir's classroom message**:

A browser is only one way to interact with an application.

Behind every browser interaction, there may be multiple API calls, business services and database operations.

A good SDET understands the complete application architecture.

- Test the UI to understand user experience.
- Test APIs to validate service contracts.
- Test databases to validate persistence.
- Combine API and UI testing to validate business workflows.

**One important principle**: Don't automate only the interface. Understand and test the system behind the interface.
