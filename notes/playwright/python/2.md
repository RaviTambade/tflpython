# Python for SDETs Learning Playwright

**Theme**: Use Python features to make automation readable, reusable, and maintainable.

## 1. Understanding the SDET ecosystem

Mentor: Imagine that we are testing an e-commerce application.

A customer:

1. Opens the website.
2. Logs in.
3. Searches for a product.
4. Adds products to the cart.
5. Checks the cart total.
6. Completes checkout.

How do we automate this journey? We need three important technologies.

- Python  (Programming language) – writes automation logic
- pytest  (Test framework) – organizes, executes and reports tests
- Playwright (Browser automation) – interacts with browser and web applications

Application Under Test (AUT) : React / Angular / ASP.NET Core / Django / FastAPI

Important distinction:

- Python writes the automation instructions.
- pytest manages test execution.
- Playwright performs browser interactions.
- Assertions verify expected application behavior.

An application written in C#, Java, Python, or Node.js can be tested using Python Playwright.

## 2. Python concepts used in automation

An SDET should not just know how to click buttons using Playwright. An SDET should know how to design maintainable automation code.

| Python concept   | Application in automation           |
| ---------------- | ----------------------------------- |
| Type hints       | Clarify function inputs and outputs |
| Dictionaries     | Store test data and API payloads    |
| Dataclasses      | Represent structured test data      |
| Functions        | Reuse test operations               |
| Classes          | Implement Page Object Model         |
| Context managers | Manage browser and file resources   |
| Exceptions       | Handle meaningful failures          |
| Yield fixtures   | Setup and teardown                  |
| Modules          | Organize reusable automation code   |

### Mentor's example: Test data

Suppose we want to test a login page.

```
user = {
    "username": "ravi",
    "password": "secret123"
}

def login(username: str, password: str) -> None:
    print(f"Logging in as {username}")

login(user["username"],user["password"])
```

Mentor : Why use a dictionary instead of hardcoding values inside every test?

Student: We can separate test data from test logic, reuse it, and maintain multiple test scenarios easily.

### Dataclasses for structured test data

```
from dataclasses import dataclass

@dataclass
class User:
    username: str
    password: str
    role: str

user = User(username="ravi", password="secret123", role="admin")

print(user.username)
print(user.role)
```

A dataclass makes structured test data easier to understand.

Remember: Python type hints and dataclasses do not automatically validate external API responses. Validate untrusted response data explicitly.

### login_page.py

```
from playwright.sync_api import Page

class LoginPage:

    def __init__(self, page: Page) -> None:
        self.page = page
        self.username = page.get_by_label("Username")
        self.password = page.get_by_label("Password")
        self.submit = page.get_by_role("button",name="Sign in" )

    def open(self, base_url: str) -> None:
        self.page.goto(f"{base_url}/Account/Login")

    def sign_in(self,username: str,password: str) -> None:

        self.username.fill(username)
        self.password.fill(password)
        self.submit.click()
```

### Understanding the design

| Component    | Responsibility                |
| ------------ | ----------------------------- |
| `LoginPage`  | Represents login page         |
| `__init__()` | Initializes page and locators |
| `open()`     | Navigates to login page       |
| `sign_in()`  | Performs login operation      |
| `Page`       | Playwright browser page       |

Mentor's observation:

Page Object Model separates two responsibilities:

- How to interact with the page.
- What behavior we expect from the application.

The first belongs in the page object. The second normally belongs in the test.

## 4. Browser automation and synchronization

Consider the following automation:

```
page.goto("http://127.0.0.1:8000")
page.get_by_role("button", name="Add to cart").click()
```

Does Playwright execute these operations without synchronization?  No. Playwright automatically waits for many browser actions to become actionable and supports retrying assertions.

### Avoid fixed sleeps

Bad approach:

```
import timetime.sleep(5)
```

Better approach:

```
from playwright.sync_api import expect

expect(page.get_by_test_id("cart-count")).to_have_text("1")
```

Why? 

The first approach waits five seconds regardless of whether the application is ready. The second approach waits for the expected condition, subject to the assertion timeout.

### Practical test

```
from playwright.sync_api import Page, expect

def test_cart_total(page: Page) -> None:

    page.goto("http://127.0.0.1:8000")

    page.get_by_role("button", name="Add to cart").click()

    expect(page.get_by_test_id("cart-count")).to_have_text("1")
```

Mentor tip: Prefer accessible roles, labels and names. Use `data-testid` when a reliable user-facing locator is unavailable.

## 5. Organizing the automation project

A professional automation project should have a meaningful structure.

```
PlaywrightAutomation/
│
├── tests/
│   ├── conftest.py
│   ├── test_login.py
│   └── test_cart.py
│
├── pages/
│   ├── login_page.py
│   └── cart_page.py
│
├── test_data/
│   └── users.py
│
├── utils/
│   └── config.py
│
├── pytest.ini
│
└── requirements.txt
```

### Responsibility of each folder

| Folder/File      | Responsibility         |
| ---------------- | ---------------------- |
| tests            | Test scenarios         |
| pages            | Page Object classes    |
| test_data        | Test input data        |
| utils            | Common utilities       |
| conftest.py      | Shared pytest fixtures |
| pytest.ini       | pytest configuration   |
| requirements.txt | Project dependencies   |

## 6. Practical example – E-commerce cart testing

Let's automate a real user journey.

Scenario: Add a keyboard to the shopping cart and verify the result.

```
from playwright.sync_api import Page, expect

def test_add_product_to_cart(page: Page) -> None:
    page.goto("http://127.0.0.1:8000/products")
    page.get_by_role("button", name="Add Keyboard to cart").click()
    expect(page.get_by_test_id("cart-count")).to_have_text("1")
    page.get_by_role("link",name="View cart").click()
    expect(page.get_by_role("heading",name="Your cart")).to_be_visible()
    expect(page.get_by_text("Keyboard")).to_be_visible()
```

### What are we actually testing?

| Step              | Expected outcome        |
| ----------------- | ----------------------- |
| Open products     | Product page is visible |
| Click Add to cart | Product is added        |
| Verify cart count | Count becomes 1         |
| View cart         | Cart page opens         |
| Verify product    | Keyboard is displayed   |

Notice one important thing:

A successful click does not mean a successful business operation. We must verify the expected outcome.

## 10. Ravi Sir's classroom discussion

Mentor: Suppose tomorrow our application changes from ASP.NET Core MVC to React. Should we rewrite our entire automation framework?

Student: No, Sir. We should mainly update page locators and interactions where the UI changes.

Mentor: Correct! What if the business requirement changes?

Student: Then we update our test scenarios and expected outcomes.

Mentor: Excellent. This is the difference between writing automation scripts and engineering an automation solution.

> A good SDET does not simply automate clicks. A good SDET understands application behavior, business rules, data flow and expected outcomes.

Remember: Automation is not about reducing testing effort alone. It is about increasing confidence in software quality.
