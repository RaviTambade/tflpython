## 4. Step 3 – Create your first TypeScript test

Create `tests/login.spec.ts`.

```
import { test, expect } from '@playwright/test';

test('Verify login page', async ({ page }) => {

    await page.goto('http://localhost:5000/Account/Login');

    await expect(page).toHaveTitle(/Login/);

    await expect(
        page.getByRole('button', { name: 'Login' })
    ).toBeVisible();

});
```

Run:

```
npx playwright test
```

Run with browser visible:

```
npx playwright test --headed
```

Run in interactive UI mode:

```
npx playwright test --ui
```

Mentor explanation:

| Code            | Meaning                        |
| --------------- | ------------------------------ |
| `test()`        | Defines a test case            |
| `async`         | Enables asynchronous execution |
| `page`          | Browser tab abstraction        |
| `goto()`        | Navigates to URL               |
| `expect()`      | Verifies expected behavior     |
| `toBeVisible()` | Checks element visibility      |

## 5. Step 4 – Understand Locators

A locator identifies an element in the web page.

Suppose our login page contains:

```
<form>
    <label>Username</label>
    <input id="username" />

    <label>Password</label>
    <input id="password" />

    <button type="submit">Login</button>
</form>
```

Playwright provides multiple locator strategies.

```
// By ID
page.locator('#username');

// By CSS selector
page.locator('#password');

// By label
page.getByLabel('Username');

// By role
page.getByRole('button', { name: 'Login' });

// By placeholder
page.getByPlaceholder('Enter username');
```

Mentor tip: Prefer user-facing locators such as role, label and placeholder where possible. They make tests more readable and resilient.

## 6. Step 5 – Write login test cases

Let's build three scenarios.

Test 1: Valid login

```
test('Valid login', async ({ page }) => {

    await page.goto('http://localhost:5000/Account/Login');

    await page.getByLabel('Username')
        .fill('admin');

    await page.getByLabel('Password')
        .fill('Admin@123');

    await page.getByRole('button', {
        name: 'Login'
    }).click();

    await expect(page).toHaveURL(/Dashboard/);

});
```

Test 2: Invalid login

```
test('Invalid login', async ({ page }) => {

    await page.goto('http://localhost:5000/Account/Login');

    await page.getByLabel('Username')
        .fill('wronguser');

    await page.getByLabel('Password')
        .fill('wrongpassword');

    await page.getByRole('button', {
        name: 'Login'
    }).click();

    await expect(
        page.getByText('Invalid username or password')
    ).toBeVisible();

});
```

Test 3: Empty username

```
test('Empty username validation', async ({ page }) => {

    await page.goto('http://localhost:5000/Account/Login');

    await page.getByLabel('Password')
        .fill('Admin@123');

    await page.getByRole('button', {
        name: 'Login'
    }).click();

    await expect(
        page.getByText('Username is required')
    ).toBeVisible();

});
```

These examples assume the MVC page uses the specified labels and validation messages. Adapt selectors to the actual application.

## 7. Step 6 – Introduce Page Object Model (POM)

Mentor: Suppose we have 50 login test cases. Should we write the same username locator, password locator and login button locator in all 50 tests?

Student: No, Sir. We should create reusable functions.

Mentor: Exactly. This is where TypeScript classes help us.

Architecture:

```
             LOGIN TESTS
                  |
                  v
             LoginPage.ts
                  |
       +----------+----------+
       |          |          |
       v          v          v
   Username   Password    Login
   Locator    Locator     Button
                  |
                  v
          ASP.NET Core MVC
```

Create `pages/LoginPage.ts`.

```
import { Page, Locator } from '@playwright/test';

export class LoginPage {

    readonly page: Page;

    readonly username: Locator;
    readonly password: Locator;
    readonly loginButton: Locator;

    constructor(page: Page) {

        this.page = page;

        this.username = page.getByLabel('Username');

        this.password = page.getByLabel('Password');

        this.loginButton = page.getByRole('button', {
            name: 'Login'
        });
    }

    async navigate(): Promise<void> {

        await this.page.goto(
            'http://localhost:5000/Account/Login'
        );
    }

    async login(
        username: string,
        password: string
    ): Promise<void> {

        await this.username.fill(username);

        await this.password.fill(password);

        await this.loginButton.click();
    }
}
```

Now update the test.

`tests/login.spec.ts`

```
import { test, expect } from '@playwright/test';

import { LoginPage } from '../pages/LoginPage';

test('Login using Page Object Model', async ({ page }) => {

    const loginPage = new LoginPage(page);

    await loginPage.navigate();

    await loginPage.login('admin', 'Admin@123');

    await expect(page).toHaveURL(/Dashboard/);

});
```

We have separated browser interaction from test scenario logic.

## 8. Step 7 – Understand the TypeScript concepts used

| TypeScript feature | Application in Playwright   |
| ------------------ | --------------------------- |
| Import             | Import Playwright classes   |
| Class              | LoginPage                   |
| Constructor        | Initialize page objects     |
| Properties         | Store locators              |
| Methods            | Encapsulate browser actions |
| Types              | Page, Locator               |
| Async/Await        | Browser interaction         |
| Promise            | Asynchronous method result  |

This is why TypeScript is particularly useful for SDET engineers.

## 10. Step 9 – Execute and generate reports

Run all tests:

```
npx playwright test
```

Run a particular test:

```
npx playwright test login.spec.ts
```

Run Chromium only:

```
npx playwright test --project=chromium
```

Generate and open HTML report:

```
npx playwright show-report
```

Debug:

```
npx playwright test --debug
```

Expected testing lifecycle

1. Test Runner discovers test cases.
2. Browser fixture launches browser context and page.
3. Test performs browser operations.
4. Assertions verify expected results.
5. Playwright records execution results.
6. HTML report presents pass/fail details.
