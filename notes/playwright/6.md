# Mentor Session 05: Database Testing with Playwright + TypeScript + MySQL

Theme: Don't just verify what the browser displays. Verify whether the application has correctly stored the data.

Mentor asks the students:

"Suppose a user registers a product through an ASP.NET Core application. The browser displays `Product created successfully`. Is that enough to conclude that the application works correctly?"

Student: "Not necessarily, Sir. We should verify whether the product was actually inserted into MySQL."

Mentor: "Excellent! That is database testing. An SDET validates the complete data flow, not just the user interface."

## 1. Understand the architecture

Our example uses:

- Playwright + TypeScript for automation
- ASP.NET Core MVC for the user interface
- ASP.NET Core Web API for business operations
- MySQL for persistence

Important distinction: The application should normally own business operations and database writes. The test framework connects directly to the database mainly for controlled test-data setup and verification.

## 4. Create a database connection

File: `database/dbConnection.ts`

### Step 1: Configure environment variables

Install dotenv:

```
npm install dotenv
```

Create a `.env` file in the project root:

```
DB_HOST=localhost
DB_PORT=3306
DB_USER=test_user
DB_PASSWORD=your_test_password
DB_NAME=tfl_playwright_lab
```

Add `.env` to `.gitignore`. Never commit database passwords or production credentials.

Create a dedicated MySQL test user with access only to the test database.

### Step 2: Create the connection pool

File: `database/dbConnection.ts`

```
import 'dotenv/config';

import mysql from 'mysql2/promise';

export const pool = mysql.createPool({
    host: process.env.DB_HOST,
    port: Number(process.env.DB_PORT || 3306),
    user: process.env.DB_USER,
    password: process.env.DB_PASSWORD,
    database: process.env.DB_NAME,

    waitForConnections: true,
    connectionLimit: 10,
    queueLimit: 0
});
```

Mentor explains:

Why use a connection pool?

Imagine 50 test cases executing simultaneously. Opening a new database connection for every query creates unnecessary overhead. A pool manages reusable database connections.

```
           Playwright Test Runner
                     |
          +----------+----------+
          |          |          |
          v          v          v
        Test 1     Test 2     Test 3
          |          |          |
          +----------+----------+
                     |
                     v
               MySQL Pool
                     |
           +---------+---------+
           |         |         |
           v         v         v
        MySQL     MySQL     MySQL
      Connection Connection Connection
```

## 5. Create a Product Repository for test verification

File: `database/productRepository.ts`

```
import { pool } from './dbConnection';

export interface ProductRecord {
    product_id: number;
    product_name: string;
    price: string;
    quantity: number;
}

export async function getProductByName(
    productName: string
): Promise<ProductRecord | undefined> {

    const [rows] = await pool.execute(
        `SELECT product_id, product_name, price, quantity
         FROM products
         WHERE product_name = ?`,
        [productName]
    );

    const products = rows as ProductRecord[];

    return products[0];
}

export async function deleteProductByName(
    productName: string
): Promise<void> {

    await pool.execute(
        `DELETE FROM products WHERE product_name = ?`,
        [productName]
    );
}
```

Notice the question mark in the SQL query.

```
WHERE product_name = ?
```

This is a parameterized query. It avoids building SQL by concatenating untrusted input and helps prevent SQL injection.

## 7. Important SDET scenario: API operation + database validation

Now comes the interesting part.

Suppose the user creates a product through the ASP.NET Core Web API.

We need to verify two things:

1. API returns the expected response.
2. The product is correctly stored in MySQL.

### Execution sequence

```
       Playwright API Test
                |
                v
       POST /api/products
                |
                v
       ASP.NET Core Web API
                |
                v
        Product Service
                |
                v
          MySQL INSERT
                |
                v
         HTTP 201 Created
                |
                v
       Playwright receives
          API response
                |
                v
       Query MySQL directly
                |
                v
       Verify stored record
                |
                v
          Test Passed
```

### Step 1: Write the API + DB integration test

Create:

`tests/api/product-database.spec.ts`

```
import { test, expect } from '@playwright/test';

import {
    getProductByName,
    deleteProductByName
} from '../../database/productRepository';

import { randomUUID } from 'node:crypto';

test('Create product and verify database record', async ({ request }) => {

    const productName = `Keyboard-${randomUUID()}`;

    const productData = {
        productName: productName,
        price: 1500,
        quantity: 25
    };

    try {

        // Step 1: Create product through Web API
        const response = await request.post(
            'https://localhost:7001/api/products',
            {
                data: productData
            }
        );

        // Step 2: Verify HTTP response
        expect(response.status()).toBe(201);

        // Step 3: Read product directly from MySQL
        const product = await getProductByName(productName);

        // Step 4: Verify database record
        expect(product).toBeDefined();

        expect(product?.product_name).toBe(productName);

        expect(Number(product?.price)).toBe(1500);

        expect(product?.quantity).toBe(25);

    }
    finally {

        // Step 5: Clean up test data
        await deleteProductByName(productName);

    }

});
```

Important assumptions: This example assumes the API accepts `productName`, `price`, and `quantity`, returns HTTP 201 on successful creation, and uses the URL shown. Adjust these to your actual ASP.NET Core API contract.

Notice something important: the test does not insert the product directly into MySQL. It uses the API to perform the business operation, then queries MySQL to verify persistence.

## 8. Extend database validation to CRUD operations

A good SDET should validate all four CRUD operations.

| Operation | API request | Database validation            |
| --------- | ----------- | ------------------------------ |
| Create    | POST        | Verify new record              |
| Read      | GET         | Compare API data with DB       |
| Update    | PUT         | Verify updated columns         |
| Delete    | DELETE      | Verify record no longer exists |

For example, after updating a product:

```
const updateResponse = await request.put(
    `https://localhost:7001/api/products/${productId}`,
    {
        data: {
            productName: productName,
            price: 1800,
            quantity: 40
        }
    }
);

expect(updateResponse.status()).toBe(200);

const updatedProduct = await getProductByName(productName);

expect(Number(updatedProduct?.price)).toBe(1800);
expect(updatedProduct?.quantity).toBe(40);
```

Here, `productId` must come from the API response or a prior database lookup. The expected status code must match the actual API contract.

For delete:

```
const deleteResponse = await request.delete(
    `https://localhost:7001/api/products/${productId}`
);

expect(deleteResponse.status()).toBe(204);

const deletedProduct = await getProductByName(productName);

expect(deletedProduct).toBeUndefined();
```

## 9. Test data management – a critical SDET responsibility

Imagine 20 students running the same automation tests simultaneously.

If every student creates a product named `Keyboard`, the tests may interfere with one another.

How do we solve this?

Use unique test data.

```
import { randomUUID } from 'node:crypto';

const productName = `TestProduct-${randomUUID()}`;
```

Use these principles:

1. Generate unique test records.
2. Never use production data for destructive testing.
3. Clean up test records after execution.
4. Use parameterized SQL queries.
5. Keep database credentials outside source code.
6. Make tests independent and safe to run in parallel.
7. Use a dedicated test database.

### Database testing best practices

Test data isolation

Each test should create and manage its own data.

Data integrity

Validate stored values, constraints and relationships.

Cleanup

Remove temporary records, even when assertions fail.

Security

Use restricted test credentials and parameterized SQL.

## 10. Understand different levels of testing

Students often confuse API testing with database testing.

| Testing type        | What are we verifying?                        |
| ------------------- | --------------------------------------------- |
| Unit testing        | Individual method or business logic           |
| API testing         | HTTP request and response                     |
| UI testing          | Browser interaction and rendered output       |
| Database testing    | Stored records, constraints and relationships |
| Integration testing | Interaction between application components    |
| End-to-end testing  | Complete user journey                         |

For example, a product purchase journey might look like this:

```
Customer
   |
   v
Browser UI
   |
   v
Playwright UI Test
   |
   v
ASP.NET Core MVC
   |
   v
ASP.NET Core Web API
   |
   v
Order Service
   |
   +-----------> Product Service
   |                   |
   v                   v
Order Repository   Product Repository
   |                   |
   +----------+--------+
              |
              v
           MySQL
              |
              v
       Verify Order Data
       Verify Product Stock
```

One important lesson: direct database verification is useful, but it does not replace testing through the application's public APIs and user workflows.

## 11. Execute the tests

```
# Run database connectivity tests
npx playwright test tests/database

# Run API + database tests
npx playwright test tests/api/product-database.spec.ts

# Run all tests
npx playwright test

# Run with browser visible
npx playwright test --headed

# Debug a test
npx playwright test --debug

# Generate HTML report
npx playwright show-report
```

When using a shared pool, close it after the relevant test suite has finished. For example, in `product-database.spec.ts`:

```
import { test } from '@playwright/test';
import { pool } from '../../database/dbConnection';

test.afterAll(async () => {
    await pool.end();
});
```

Do not close a shared pool after every individual test if other tests still need it.

## 13. Mentor's closing message

Student: Sir, earlier we were checking whether the browser displayed the correct message. Now we are checking whether the actual business data is correct.

Mentor: Exactly!

A professional SDET asks three questions:

1. Did the user interface behave correctly?
2. Did the API process the request correctly?
3. Did the database persist the correct information?

> A successful HTTP response does not automatically mean successful business processing.

The SDET must verify the complete journey.
