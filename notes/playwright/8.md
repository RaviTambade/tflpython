# Mentor Session 06: Playwright Advanced Authentication, Parallel Execution and Test Data Strategy

Theme: A professional SDET must test not only whether an application works, but also whether it works correctly for different users, roles and concurrent sessions.

Mentor asks:

"Suppose our TFLCoMentor application has 500 students, 20 mentors and 5 administrators. Should we test every feature using only one login account?"

Student: "No, Sir. Different users have different permissions."

Mentor: "Correct. We must understand authentication, authorization, test isolation and parallel execution."

## 1. Authentication vs Authorization

These two concepts are often confused.

| Authentication       | Authorization           |
| -------------------- | ----------------------- |
| Who are you?         | What can you do?        |
| Verifies identity    | Checks permissions      |
| Login, password, JWT | Roles, policies, claims |
| 401 Unauthorized     | 403 Forbidden           |

Example:

- Student logs in successfully.
- Student requests the mentor dashboard.
- Server identifies the student but denies access.
- Expected result: `403 Forbidden` if the endpoint uses role-based authorization.

```
             User Login
                 |
                 v
          Authentication
                 |
                 v
           Validate User
                 |
                 v
           Issue JWT Token
                 |
                 v
          Access API Endpoint
                 |
                 v
           Authorization
                 |
         +-------+-------+
         |               |
         v               v
      Allowed          Denied
         |               |
         v               v
     HTTP 200         HTTP 403
```

## 2. Understand JWT authentication

JWT means JSON Web Token.

A typical authentication flow:

```
Playwright Test
      |
      | POST /api/auth/login
      v
ASP.NET Core Web API
      |
      v
Validate Credentials
      |
      v
Generate JWT
      |
      v
Return Access Token
      |
      v
Playwright Stores Token
      |
      | Authorization: Bearer <token>
      v
Protected API Endpoint
      |
      v
Validate Token + Claims
      |
      v
Return Protected Resource
```

Example login response:

```
{
  "accessToken": "eyJhbGciOiJIUzI1NiIs...",
  "tokenType": "Bearer"
}
```

The token is illustrative. A real application must validate signature, expiry, issuer, audience and relevant claims.

## 3. Write a Playwright JWT authentication test

Create:

`tests/api/auth.spec.ts`

```
import { test, expect } from '@playwright/test';

test('Student can access authorized API', async ({ request }) => {

    const loginResponse = await request.post(
        'https://localhost:7001/api/auth/login',
        {
            data: {
                username: 'student1',
                password: process.env.STUDENT_PASSWORD
            }
        }
    );

    expect(loginResponse.status()).toBe(200);

    const loginData = await loginResponse.json();

    const token = loginData.accessToken;

    expect(token).toBeTruthy();

    const profileResponse = await request.get(
        'https://localhost:7001/api/student/profile',
        {
            headers: {
                Authorization: `Bearer ${token}`
            }
        }
    );

    expect(profileResponse.status()).toBe(200);

});
```

Use a dedicated test account and store its password in an environment variable, not in source control. This example assumes the login and profile routes match your API.

## 4. Test authorization boundaries

An SDET should verify both successful and denied access.

| User                 | Endpoint           | Expected result |
| -------------------- | ------------------ | --------------- |
| Student              | Student profile    | 200             |
| Student              | Mentor dashboard   | 403             |
| Mentor               | Mentor dashboard   | 200             |
| Admin                | Admin dashboard    | 200             |
| Unauthenticated user | Protected endpoint | 401             |

Example:

```
test('Student cannot access mentor dashboard', async ({ request }) => {

    const loginResponse = await request.post(
        'https://localhost:7001/api/auth/login',
        {
            data: {
                username: 'student1',
                password: process.env.STUDENT_PASSWORD
            }
        }
    );

    const loginData = await loginResponse.json();

    const response = await request.get(
        'https://localhost:7001/api/mentor/dashboard',
        {
            headers: {
                Authorization: `Bearer ${loginData.accessToken}`
            }
        }
    );

    expect(response.status()).toBe(403);

});
```

The exact response depends on the server's authentication and authorization configuration. Test the application's actual security contract.

## 5. Reusable authenticated API fixture

Instead of logging in separately in every test, we can build a custom fixture.

File: `fixtures/authFixtures.ts`

```
import {
    test as base,
    expect,
    APIRequestContext
} from '@playwright/test';

type AuthFixtures = {
    studentApi: APIRequestContext;
};

export const test = base.extend<AuthFixtures>({

    studentApi: async ({ playwright }, use) => {

        const api = await playwright.request.newContext({
            baseURL: 'https://localhost:7001',
            ignoreHTTPSErrors: true
        });

        try {

            const response = await api.post('/api/auth/login', {
                data: {
                    username: 'student1',
                    password: process.env.STUDENT_PASSWORD
                }
            });

            if (!response.ok()) {
                throw new Error('Student authentication failed');
            }

            const data = await response.json();

            await api.dispose();

            const authenticatedApi =
                await playwright.request.newContext({
                    baseURL: 'https://localhost:7001',
                    extraHTTPHeaders: {
                        Authorization: `Bearer ${data.accessToken}`
                    },
                    ignoreHTTPSErrors: true
                });

            try {
                await use(authenticatedApi);
            }
            finally {
                await authenticatedApi.dispose();
            }

        }
        finally {
            // The initial login context is disposed above.
        }
    }

});

export { expect };
```

A cleaner production-ready version uses a single request context and applies the authorization header after login:

```
import {
    test as base,
    expect,
    APIRequestContext
} from '@playwright/test';

type AuthFixtures = {
    studentApi: APIRequestContext;
};

export const test = base.extend<AuthFixtures>({

    studentApi: async ({ playwright }, use) => {

        const api = await playwright.request.newContext({
            baseURL: 'https://localhost:7001',
            ignoreHTTPSErrors: true
        });

        try {

            const loginResponse = await api.post('/api/auth/login', {
                data: {
                    username: 'student1',
                    password: process.env.STUDENT_PASSWORD
                }
            });

            if (!loginResponse.ok()) {
                throw new Error('Student login failed');
            }

            const data = await loginResponse.json();

            await api.setExtraHTTPHeaders({
                Authorization: `Bearer ${data.accessToken}`
            });

            await use(api);

        }
        finally {
            await api.dispose();
        }

    }

});

export { expect };
```

Now use it:

```
import { test, expect } from '../../fixtures/authFixtures';

test('Student views profile', async ({ studentApi }) => {

    const response = await studentApi.get('/api/student/profile');

    expect(response.status()).toBe(200);

});
```

This fixture logs in once per test invocation, not once for the entire test suite. That provides better isolation.

## 6. Browser authentication using Storage State

Now let's move from API authentication to browser authentication.

Imagine 30 UI test cases need an authenticated student session.

Should every test repeat the login steps?

Not necessarily. Playwright supports browser storage state, which can preserve authentication-related browser state such as cookies and local storage.

### Authentication architecture

```
             Authentication Setup
                     |
                     v
             Open Login Page
                     |
                     v
              Enter Credentials
                     |
                     v
                Submit Login
                     |
                     v
              Successful Login
                     |
                     v
            Save Storage State
                     |
                     v
             student-auth.json
                     |
          +----------+----------+
          |          |          |
          v          v          v
        Test 1     Test 2     Test 3
          |          |          |
          +----------+----------+
                     |
                     v
           Reuse Authenticated State
```

### Step 1: Create authentication setup

Create `tests/auth.setup.ts`:

```
import { test as setup, expect } from '@playwright/test';

const authFile = 'playwright/.auth/student.json';

setup('Authenticate student', async ({ page }) => {

    await page.goto('http://localhost:5000/Account/Login');

    await page.getByLabel('Username').fill('student1');

    await page.getByLabel('Password').fill(
        process.env.STUDENT_PASSWORD!
    );

    await page.getByRole('button', { name: 'Login' }).click();

    await expect(page).toHaveURL(/Dashboard/);

    await page.context().storageState({
        path: authFile
    });

});
```

### Step 2: Configure Playwright projects

Update `playwright.config.ts`:

```
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({

    testDir: './tests',

    fullyParallel: true,

    workers: 4,

    use: {
        baseURL: 'http://localhost:5000',
        trace: 'on-first-retry'
    },

    projects: [

        {
            name: 'setup',
            testMatch: /auth\.setup\.ts/
        },

        {
            name: 'chromium',
            use: {
                ...devices['Desktop Chrome'],
                storageState: 'playwright/.auth/student.json'
            },
            dependencies: ['setup'],
            testIgnore: /auth\.setup\.ts/
        }

    ]

});
```

The setup project runs first. The Chromium project depends on it and uses the saved authentication state.

Important security points:

- Add `playwright/.auth/` to `.gitignore`.
- Never commit authentication state files.
- Use dedicated test accounts.
- A shared authenticated account may cause interference if tests modify the same user data.
- If authentication uses session storage, note that Playwright's standard storage-state mechanism does not automatically persist session storage.

## 7. Understand Parallel Execution

Suppose 100 test cases are available.

Sequential execution:

```
Test 1 → Test 2 → Test 3 → Test 4 → ... → Test 100
```

Parallel execution:

```
              Playwright Runner
                      |
             +--------+--------+
             |        |        |
             v        v        v
          Worker 1 Worker 2 Worker 3
             |        |        |
             v        v        v
          Test 1   Test 2   Test 3
          Test 4   Test 5   Test 6
          Test 7   Test 8   Test 9
```

Instead of one worker executing every test, multiple workers execute independent tests concurrently.

Configure workers:

```
export default defineConfig({

    workers: 4,

    fullyParallel: true,

    retries: 1,

});
```

Run with a specified number of workers:

```
npx playwright test --workers=4
```

Run tests sequentially:

```
npx playwright test --workers=1
```

### Mentor explains

Parallel execution improves speed, but introduces a new engineering challenge: shared data.

Suppose two tests both update the same product.

```
Test A                  Test B
  |                       |
  v                       v
Update Product 12      Update Product 12
  |                       |
  v                       v
Price = 1500           Price = 2000
  |                       |
  +-----------+-----------+
              |
              v
         Data Conflict
```

Both tests may pass individually but fail when executed together.

The solution is test isolation.

## 8. Build unique test data for parallel workers

Use the worker index and test identity to generate unique test records.

```
import { test, expect } from '@playwright/test';

import { randomUUID } from 'node:crypto';

test('Create independent product', async ({
    request
}, testInfo) => {

    const productName =
        `Product-W${testInfo.workerIndex}-${randomUUID()}`;

    const response = await request.post(
        'https://localhost:7001/api/products',
        {
            data: {
                productName,
                price: 1200,
                quantity: 10
            }
        }
    );

    expect(response.status()).toBe(201);

});
```

Each test receives a unique product name.

For more complex applications, create a dedicated test-data factory.

`testdata/productFactory.ts`

```
import { randomUUID } from 'node:crypto';

export interface Product {
    productName: string;
    price: number;
    quantity: number;
}

export function createProduct(): Product {

    return {
        productName: `Product-${randomUUID()}`,
        price: 1500,
        quantity: 20
    };

}
```

Now test data generation is reusable:

```
import { test, expect } from '@playwright/test';

import { createProduct } from '../../testdata/productFactory';

test('Create product using test data factory', async ({ request }) => {

    const product = createProduct();

    const response = await request.post(
        'https://localhost:7001/api/products',
        { data: product }
    );

    expect(response.status()).toBe(201);

});
```

## 9. Understand Test Isolation

A good automation framework should follow these rules:

| Resource        | Recommended approach                  |
| --------------- | ------------------------------------- |
| Browser         | Reuse Playwright-managed browser      |
| Browser context | Isolate between tests                 |
| Page            | Use a fresh page per test             |
| Test user       | Separate accounts where necessary     |
| Product records | Unique test data                      |
| Database        | Dedicated test environment            |
| Authentication  | Avoid shared mutable sessions         |
| Cleanup         | Delete only records owned by the test |

Golden rule: A test should not depend on another test having executed first.

## 10. Build a role-based testing matrix for TFLCoMentor

Let's apply these concepts to the real learning platform.

| Feature                   | Student | Mentor       | Admin |
| ------------------------- | ------- | ------------ | ----- |
| View own profile          | Yes     | Yes          | Yes   |
| Take assessment           | Yes     | No           | Yes   |
| Review student assessment | No      | Yes          | Yes   |
| Manage questions          | No      | SME/Mentor\* | Yes   |
| Manage users              | No      | No           | Yes   |
| View own learning plan    | Yes     | No           | Yes   |

The exact permissions should follow your application's authorization policy.

A role-based test architecture:

```
                 TFLCoMentor
                      |
              Authentication API
                      |
                  JWT Token
                      |
              Authorization Layer
                      |
          +-----------+-----------+
          |           |           |
          v           v           v
       Student      Mentor       Admin
          |           |           |
          v           v           v
      Dashboard   Assessment    User Mgmt
          |           |           |
          +-----------+-----------+
                      |
                Playwright Tests
                      |
                Validate Access
```

An SDET should test both positive and negative authorization scenarios. For example, a student should not be able to access another student's private assessment merely by changing an ID in the URL.
