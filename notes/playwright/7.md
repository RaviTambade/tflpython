## 4. Concept 1 – JWT Authentication using TypeScript

Consider a student logging into the assessment portal.

```
React Login Page
       |
       v
POST /api/auth/login
       |
       v
ASP.NET Core API
       |
       v
Validate Credentials
       |
       v
Generate JWT
       |
       v
Return Access Token
       |
       v
Playwright Authentication Setup
```

### Practical implementation

Create `tests/auth.setup.ts`.

```
import { test as setup, expect } from '@playwright/test';
import type { LoginRequest, LoginResponse } from '../utils/models';

const authFile = 'playwright/.auth/student.json';

setup('authenticate student', async ({ request, page }) => {

    const credentials: LoginRequest = {
        username: process.env.TEST_USERNAME!,
        password: process.env.TEST_PASSWORD!
    };

    const response = await request.post('http://localhost:5000/api/auth/login', {data: credentials});
    expect(response.ok()).toBeTruthy();
    const result = await response.json() as LoginResponse;
    expect(result.accessToken).toBeTruthy();

    // Inject JWT before React application starts.
    await page.addInitScript((token: string) => {
        localStorage.setItem('accessToken', token);
    }, result.accessToken);

    await page.goto('http://localhost:5173');

    await expect(page).toHaveURL(/localhost:5173/);

    // Save authentication state.
    await page.context().storageState({path: authFile});

});
```

Set environment variables in your terminal before execution.

PowerShell:

```
$env:TEST_USERNAME="student01"
$env:TEST_PASSWORD="Test@123"
```

Important: The non-null assertion operator `!` tells TypeScript that the environment variable is present. It does not validate it at runtime. In production-quality test code, explicitly check that both variables exist before making the API request.

Also, create the `playwright/.auth` directory before running setup.

## 5. Concept 2 – Storage State and Authentication Reuse

Instead of logging in for every test, we can reuse the saved authentication state.

### Configure `playwright.config.ts`

```
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({

    testDir: './tests',
    fullyParallel: true,
    workers: 4,
    retries: 1,
    reporter: 'html',

    use: {
        baseURL: 'http://localhost:5173',
        trace: 'retain-on-failure',
        screenshot: 'only-on-failure'
    },

    projects: [
        {   name: 'setup', testMatch: /auth\.setup\.ts/ },
        {
            name: 'chromium',
            use: {...devices['Desktop Chrome'],storageState: 'playwright/.auth/student.json'},
            dependencies: ['setup'],
            testIgnore: /auth\.setup\.ts/
        }
    ]

});
```

### Execution sequence

```
       Playwright Test Runner
                 |
                 v
           Setup Project
                 |
                 v
           Login API Call
                 |
                 v
            Generate JWT
                 |
                 v
          Save Storage State
                 |
          +------+------+------+
          |      |      |      |
          v      v      v      v
        Test 1 Test 2 Test 3 Test 4
          |      |      |      |
          +------+------+------+
                 |
                 v
            HTML Report
```

Remember:

- Each test gets an isolated browser context.
- Authentication state can be reused.
- The JWT can expire.
- Backend token revocation can affect multiple tests.
- Storage state is sensitive and must not be committed to Git.
- Session storage is not included automatically.

For an HTTP-only cookie implementation, authenticate through the cookie-based login flow and save the context's cookies instead of injecting a JWT into localStorage.

## 6. Concept 3 – Playwright Fixtures using TypeScript

A fixture is a reusable dependency supplied to a test. For example, every student assessment test may need:

- An authenticated browser page.
- Student information.
- An assessment URL.
- A reusable page object.

### Built-in fixtures

```
import { test, expect } from '@playwright/test';

test('Verify dashboard', async ({ page, browser, context }) => {
    await page.goto('/dashboard');
    await expect(page.getByRole('heading', {name: 'Student Dashboard'})).toBeVisible();

});
```

| Fixture       | Type / Purpose         |
| ------------- | ---------------------- |
| `page`        | Page                   |
| `browser`     | Browser                |
| `context`     | BrowserContext         |
| `request`     | APIRequestContext      |
| `browserName` | Browser identification |

### Create custom fixtures

Create `fixtures/student.fixture.ts`.

```
import { test as base, expect } from '@playwright/test';

interface StudentFixtures {
    studentName: string;
    assessmentUrl: string;
}

export const test = base.extend<StudentFixtures>({
    studentName: async ({}, use) => {
        const name = 'Transflower Student';
        await use(name);
    },
    assessmentUrl: async ({ baseURL }, use) => {await use(`${baseURL}/assessments`);}
});

export { expect };
```

Use the fixture:

```
import { test, expect} from '../fixtures/student.fixture';

test('Verify student assessment page', async ({ page,studentName,assessmentUrl}) => {
    console.log(studentName);
    await page.goto(assessmentUrl);
    await expect(page.getByText('My Assessments')).toBeVisible();
});
```

### Understand TypeScript generics in fixtures

```
base.extend<StudentFixtures>()
```

Here `StudentFixtures` describes the additional fixture properties available to test cases. This gives us compile-time type checking and better IntelliSense support in VS Code.

### Fixture lifecycle

```
       Test Starts
           |
           v
    Fixture Initialization
           |
           v
      use(fixture)
           |
           v
      Execute Test
           |
           v
     Fixture Teardown
           |
           v
       Test Ends
```

## 7. Concept 4 – Page Object Model using TypeScript

Now we will create reusable page classes.

Create `pages/LoginPage.ts`.

```
import { Page, Locator } from '@playwright/test';

export class LoginPage {

    private readonly page: Page;

    private readonly username: Locator;
    private readonly password: Locator;
    private readonly loginButton: Locator;

    constructor(page: Page) {

        this.page = page;
        this.username = page.getByLabel('Username');
        this.password = page.getByLabel('Password');
        this.loginButton = page.getByRole('button', { name: 'Login' });

    }

    async navigate(): Promise<void> {
        await this.page.goto('/login');
    }

    async login( username: string, password: string): Promise<void> {
        await this.username.fill(username);
        await this.password.fill(password);
        await this.loginButton.click();
    }

}
```

Create `pages/AssessmentPage.ts`.

```
import { Page, Locator } from '@playwright/test';

export class AssessmentPage {

    private readonly page: Page;

    private readonly nextButton: Locator;
    private readonly submitButton: Locator;

    constructor(page: Page) {

        this.page = page;

        this.nextButton = page.getByRole('button', {name: 'Next' });

        this.submitButton = page.getByRole('button', { name: 'Submit Assessment' });

    }

    async navigate(assessmentId: number): Promise<void> {
        await this.page.goto(`/assessment/${assessmentId}`);
    }

    async selectAnswer(option: string): Promise<void> {
        await this.page.getByLabel(option).check();
    }

    async nextQuestion(): Promise<void> {
        await this.nextButton.click();
    }

    async submitAssessment(): Promise<void> {
        await this.submitButton.click();
    }

}
```

Use the page object:

```
import { test, expect } from '@playwright/test';
import { LoginPage } from '../pages/LoginPage';

test('Student login using POM', async ({ page }) => {
    const loginPage = new LoginPage(page);
    await loginPage.navigate();
    await loginPage.login('student01', 'Test@123');
    await expect(page).toHaveURL(/dashboard/);
});
```

Mentor insight: Page classes contain UI interaction logic. Test classes contain test scenarios and expected outcomes. This separation makes maintenance easier.

## 8. Concept 5 – Parallel execution using TypeScript

Suppose Transflower has 100 automated test cases. Sequential execution:

```
Test 1 → Test 2 → Test 3 → Test 4 → ... → Test 100
```

Parallel execution:

```
              Playwright Runner
                     |
          +----------+----------+
          |          |          |
          v          v          v
       Worker 0   Worker 1   Worker 2
          |          |          |
          v          v          v
        Test 1     Test 2     Test 3
        Test 4     Test 5     Test 6
        Test 7     Test 8     Test 9
```

### Configure parallel execution

```
import { defineConfig } from '@playwright/test';

export default defineConfig({
    fullyParallel: true,
    workers: 4,
    retries: 1,
    timeout: 30000,
    reporter: 'html'
});
```

Execute tests:

```
# Execute all tests
npx playwright test

# Execute using two workers
npx playwright test --workers=2

# Execute using four workers
npx playwright test --workers=4

# Execute in headed mode
npx playwright test --headed

# Debug execution
npx playwright test --debug
```

### Understand worker properties

| Property        | Meaning                            |
| --------------- | ---------------------------------- |
| `workerIndex`   | Unique worker process index        |
| `parallelIndex` | Parallel worker slot               |
| `workers`       | Maximum concurrent workers         |
| `fullyParallel` | Enables independent test execution |

## 9. Concept 6 – Test Data Strategy using TypeScript

This is one of the most important topics in enterprise automation. Imagine four workers creating assessment records simultaneously.

Parallel test data isolation

Worker 1

Student 101

Assessment A

Worker 2

Student 102

Assessment B

Worker 3

Student 103

Assessment C

Worker 4

Student 104

Assessment D

Independent records reduce test interference.

### A. Create a test data factory

Create `utils/dataFactory.ts`.

```
import { randomUUID } from 'node:crypto';

export interface StudentTestData {
    username: string;
    email: string;
    password: string;
}

export function createStudentTestData(workerIndex: number): StudentTestData {
    const uniqueId = randomUUID();
    return {
        username: `student_w${workerIndex}_${uniqueId}`,
        email: `student_${uniqueId}@test.com`,
        password: 'Test@123'
    };
}
```

Use it in a test:

```
import { test, expect } from '@playwright/test';
import { createStudentTestData } from '../utils/dataFactory';

test('Register unique student', async ({ page}, testInfo) => {

    const student = createStudentTestData(testInfo.workerIndex);
    await page.goto('/register');
    await page.getByLabel('Username').fill(student.username);
    await page.getByLabel('Email').fill(student.email);
    await page.getByLabel('Password').fill(student.password);
    await page.getByRole('button', {name: 'Register'}).click();
    await expect(page.getByText('Registration successful')).toBeVisible();

});
```

## 10. Concept 7 – API authentication using TypeScript

Playwright can authenticate through an API request without opening a browser.

Example:

```
import { test, expect } from '@playwright/test';

test('Verify authenticated assessment API', async ({ request}) => {

    const loginResponse = await request.post('http://localhost:5000/api/auth/login',
        {
            data: {
                username: process.env.TEST_USERNAME,
                password: process.env.TEST_PASSWORD
            }
        }
    );

    expect(loginResponse.ok()).toBeTruthy();
    const loginData = await loginResponse.json();
    const token = loginData.accessToken as string;

    const assessmentResponse = await request.get(
        'http://localhost:5000/api/assessments',
        {
            headers: {
                Authorization: `Bearer ${token}`
            }
        }
    );
    expect(assessmentResponse.status()).toBe(200);
});
```

This demonstrates API authentication and authorization testing independently of the browser. For larger test suites, use a dedicated API request fixture with an authorization header rather than repeating token setup in every API test.

## 11. Database conflicts and transaction strategy

Your MySQL database contains:

```
questions
mcq_options
tests
test_questions
assessments
studentanswers
student_assessment_results
```

Consider two workers submitting answers for the same assessment.

```
Worker 1                   Worker 2
    |                          |
    v                          v
Student 101                Student 102
    |                          |
    v                          v
Assessment 5001            Assessment 5001
    |                          |
    v                          v
Submit Answers             Submit Answers
    |                          |
    +------------+-------------+
                 |
                 v
              MySQL
                 |
                 v
          studentanswers
```

This is safe if each student has a separate assignment and answer records. It becomes problematic if both workers modify the same student's answers.

Recommended rules:

1. Assign separate student identities for independent workflows.
2. Generate unique test data for every test.
3. Avoid shared mutable assessment assignments.
4. Use database transactions for answer submission and result calculation.
5. Implement cleanup APIs for test-generated records.
6. Avoid destructive cleanup during parallel execution.

Do not assume that a database transaction automatically isolates separate Playwright workers. The test architecture must deliberately manage data ownership and cleanup.
