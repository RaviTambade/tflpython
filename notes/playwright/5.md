# Mentor Session 04: Playwright Fixtures and Test Lifecycle Using TypeScript

Topic: Build reusable test infrastructure instead of writing browser setup code in every test.

Mentor's opening question:

"Suppose we have 100 test cases for our TFLInsurance application. Should every test case independently launch a browser, open a page, log in, and close the browser?"

Student: "No, Sir. We should reuse common setup logic."

Mentor: "Exactly! That is why Playwright provides Fixtures and Test Lifecycle Hooks."

## 1. What is a Playwright Fixture?

A fixture is a reusable resource or setup mechanism provided to a test.

Examples:

- Browser
- Browser context
- Page
- API request context
- Login page object
- Authenticated user
- Test data

Think of a fixture as a classroom arrangement. Before students enter, the mentor arranges the classroom. After the session, everything is cleaned up.

### Fixture execution architecture

## 2. Understand built-in Playwright fixtures

Playwright provides commonly used fixtures automatically.

| Fixture       | Purpose                   |
| ------------- | ------------------------- |
| `browser`     | Browser instance          |
| `context`     | Isolated browser session  |
| `page`        | Browser tab/page          |
| `request`     | API request context       |
| `browserName` | Browser currently running |

Example:

```
import { test, expect } from '@playwright/test';

test('Open Transflower website', async ({ page }) => {

    await page.goto('http://localhost:5000');

    await expect(page).toHaveTitle(/Transflower/);

});
```

Mentor explains:

You did not create the browser or page manually. Playwright created and managed these resources through fixtures.

## 3. Understand Test Lifecycle Hooks

Lifecycle hooks allow us to execute common logic at different stages of test execution.

| Hook           | When it executes                              |
| -------------- | --------------------------------------------- |
| `beforeAll()`  | Once before tests in a file or describe group |
| `beforeEach()` | Before each test                              |
| `afterEach()`  | After each test                               |
| `afterAll()`   | Once after tests in a file or describe group  |

Example:

```
import { test, expect } from '@playwright/test';

test.beforeAll(async () => {
    console.log("Starting test suite");
});

test.beforeEach(async ({ page }) => {
    console.log("Opening application");

    await page.goto('http://localhost:5000');
});

test('Home page test', async ({ page }) => {

    await expect(page).toHaveTitle(/Transflower/);

});

test('About page test', async ({ page }) => {

    await page.getByRole('link', { name: 'About' }).click();

    await expect(page).toHaveURL(/About/);

});

test.afterEach(async () => {
    console.log("Test completed");
});

test.afterAll(async () => {
    console.log("Test suite completed");
});
```

Remember: `beforeAll` and `afterAll` are suite-level hooks, not per-test browser setup hooks. Use the `page` fixture in `beforeEach` when each test needs its own page.

## 4. Build a Custom Fixture

Now let's build something useful for our SDET students.

Instead of writing login steps in every test, let's create a reusable `LoginPage` fixture.

### Step 1: Create LoginPage.ts

Project location:

`pages/LoginPage.ts`

```
import { Page, Locator } from '@playwright/test';

export class LoginPage {

    readonly page: Page;
    readonly username: Locator;
    readonly password: Locator;
    readonly loginButton: Locator;

    constructor(page: Page) {

        this.page = page;

        this.username = page.getByLabel('Username');
        this.password = page.getByLabel('Password');

        this.loginButton =
            page.getByRole('button', { name: 'Login' });
    }

    async navigate() {

        await this.page.goto(
            'http://localhost:5000/Account/Login'
        );

    }

    async login(user: string, pass: string) {

        await this.username.fill(user);

        await this.password.fill(pass);

        await this.loginButton.click();

    }
}
```

### Step 2: Create custom test fixture

Create:

`fixtures/testFixtures.ts`

```
import { test as base, expect } from '@playwright/test';

import { LoginPage } from '../pages/LoginPage';

type MyFixtures = {
    loginPage: LoginPage;
};

export const test = base.extend<MyFixtures>({

    loginPage: async ({ page }, use) => {

        const loginPage = new LoginPage(page);

        await use(loginPage);

    }

});

export { expect };
```

What is happening?

1. Playwright provides the `page`.
2. We create a `LoginPage` object.
3. We expose it as a custom fixture.
4. The test uses the fixture.
5. Playwright handles fixture teardown after the test.

### Step 3: Use the custom fixture

Create:

`tests/ui/login.spec.ts`

```
import { test, expect } from '../../fixtures/testFixtures';

test('Valid user login', async ({ loginPage, page }) => {

    await loginPage.navigate();

    await loginPage.login(
        'student1',
        'Password@123'
    );

    await expect(page).toHaveURL(/Dashboard/);

});
```

Reusable test infrastructure

We have separated:

- Page interaction logic → `LoginPage.ts`
- Fixture setup → `testFixtures.ts`
- Test scenario → `login.spec.ts`

This is a maintainable SDET framework structure.

## 5. Understand Fixture Scope

A very important concept for professional automation engineers.

| Scope        | Meaning                               | Example                                       |
| ------------ | ------------------------------------- | --------------------------------------------- |
| Test scope   | Created for each test                 | Page, browser context                         |
| Worker scope | Shared by tests running in one worker | Read-only test configuration, worker resource |

A worker-scoped fixture example:

```
import { test as base } from '@playwright/test';

type WorkerFixtures = {
    environmentName: string;
};

export const test = base.extend<{}, WorkerFixtures>({

    environmentName: [
        async ({}, use) => {

            console.log('Preparing worker environment');

            await use('QA');

            console.log('Cleaning worker environment');

        },
        { scope: 'worker' }
    ]

});
```

Use worker scope carefully. Do not share mutable browser pages or test-user state between parallel tests unless you have designed that isolation explicitly.

## 6. API Fixture Example

We can also create reusable API setup for our ASP.NET Core Web API.

`fixtures/apiFixtures.ts`

```
import {
    test as base,
    APIRequestContext,
    expect
} from '@playwright/test';

type ApiFixtures = {
    api: APIRequestContext;
};

export const test = base.extend<ApiFixtures>({

    api: async ({ playwright }, use) => {

        const api = await playwright.request.newContext({
            baseURL: 'https://localhost:7001',
            ignoreHTTPSErrors: true
        });

        await use(api);

        await api.dispose();

    }

});

export { expect };
```

`ignoreHTTPSErrors` is appropriate only for a controlled local test environment with a development certificate. Prefer trusting the certificate.

Use the fixture:

```
import { test, expect } from '../../fixtures/apiFixtures';

test('Get all products', async ({ api }) => {

    const response = await api.get('/api/products');

    expect(response.status()).toBe(200);

    const products = await response.json();

    expect(Array.isArray(products)).toBeTruthy();

});
```

## 9. Mentor's closing conversation

Student: Sir, earlier we were writing automation scripts. Now we are building an automation framework.

A script automates one scenario.
