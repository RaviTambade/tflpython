# Mentor Session 03: API Testing Using Playwright + TypeScript

TRANSFLOWER LEARNING · SDET HANDS-ON LAB

Theme: From Browser Automation to API Automation

In our previous session, we automated the Login UI using Playwright and TypeScript.

Today, let's understand an important question.

Mentor: Suppose the Login page is working perfectly. The username and password fields accept input, and the Login button responds. Does that guarantee that the authentication functionality is working correctly?

Student: Not necessarily, Sir. The backend API or database might have problems.

Mentor: Exactly! That's why an SDET should understand both UI testing and API testing.

> UI testing verifies the user experience. API testing verifies the application services and their contracts.

The important difference:

| UI Testing              | API Testing                      |
| ----------------------- | -------------------------------- |
| Uses browser            | Uses HTTP requests               |
| Tests user interactions | Tests API contracts              |
| Uses locators           | Uses endpoints                   |
| Verifies HTML           | Verifies JSON                    |
| Tests navigation        | Tests status codes and responses |
| Slower generally        | Faster generally                 |

## 2. Understand HTTP methods

Before writing API automation, understand HTTP.

| Method | Purpose        | Example              |
| ------ | -------------- | -------------------- |
| GET    | Retrieve data  | Get all products     |
| POST   | Create data    | Add a product        |
| PUT    | Update data    | Update a product     |
| PATCH  | Partial update | Update product price |
| DELETE | Delete data    | Remove a product     |

Our example API:

```
Base URL: https://localhost:7001

GET     /api/products
GET     /api/products/101
POST    /api/products
PUT     /api/products/101

```

## 3. Create a Playwright API testing project

We will continue with our existing `TFLPlaywrightLab` project.

Install Playwright if you haven't already:

```
npm install -D @playwright/test
```

The API testing capability is included in `@playwright/test`; we don't need a separate HTTP testing package.

## 4. First API test – GET request

Create `tests/products-api.spec.ts`.

```
import { test, expect } from '@playwright/test';

test('Get all products', async ({ request }) => {

    const response = await request.get(
        'https://localhost:7001/api/products'
    );

    expect(response.status()).toBe(200);

    const products = await response.json();

    expect(Array.isArray(products)).toBeTruthy();

});
```

## 5. Second API test – Verify a product by ID

```
test('Get product by ID', async ({ request }) => {

    const response = await request.get(
        'https://localhost:7001/api/products/101'
    );

    expect(response.status()).toBe(200);

    const product = await response.json();

    expect(product.id).toBe(101);

    expect(product.name).toBe('Laptop');

    expect(product.price).toBe(55000);

});
```

Mentor explanation:

We are not just checking whether the API responds. We are validating the correctness of business data.

For example:

- Is the product ID correct?
- Is the product name correct?
- Is the price correct?
- Is the response structure correct?

## 6. Third API test – POST request

Now let's create a product through the API.

```
test('Create a new product', async ({ request }) => {

    const newProduct = {
        name: 'Mechanical Keyboard',
        price: 2500,
        isAvailable: true
    };

    const response = await request.post(
        'https://localhost:7001/api/products',
        {
            data: newProduct
        }
    );

    expect(response.status()).toBe(201);

    const createdProduct = await response.json();

    expect(createdProduct.name)
        .toBe('Mechanical Keyboard');

    expect(createdProduct.price).toBe(2500);

});
```

Expected API interaction:

```

      |

      |
```

Note: This example assumes the API returns HTTP 201 and the created product in its response body.

Here we validate that the API successfully updates an existing resource.

## 8. Fifth API test – DELETE request

```
test('Delete product', async ({ request }) => {

    const response = await request.delete(
        'https://localhost:7001/api/products/101'
    );

    expect(response.status()).toBe(204);

});
```

This example assumes the API uses `204 No Content` for successful deletion.

Mentor tip: API status codes are part of the contract. Confirm the actual behavior of your ASP.NET Core API rather than assuming every application returns the same status code.

## 9. Introduce TypeScript Interfaces in API Testing

Now let's make our API tests more professional.

Instead of passing anonymous objects everywhere, define a reusable Product interface.

Create `testdata/Product.ts`.

```
export interface Product {

    id?: number;

    name: string;

    price: number;

    isAvailable: boolean;
}
```

Create test data:

`testdata/products.ts`

```
import { Product } from './Product';

export const laptop: Product = {
    name: 'Laptop',
    price: 55000,
    isAvailable: true
};

export const keyboard: Product = {
    name: 'Keyboard',
    price: 2500,
    isAvailable: true
};
```

Use it in the test:

```
import { test, expect } from '@playwright/test';

import { laptop } from '../testdata/products';

test('Create laptop product', async ({ request }) => {

    const response = await request.post(
        'https://localhost:7001/api/products',
        {
            data: laptop
        }
    );

    expect(response.status()).toBe(201);

});
```

What did we achieve?

- Reusable test data.
- Stronger type checking.
- Consistent request structure.
- Easier maintenance.

## 10. Introduce API Response Interfaces

An API response can also be represented using TypeScript.

```
export interface ProductResponse {

    id: number;

    name: string;

    price: number;

    isAvailable: boolean;
}
```

Use it:

```
const response = await request.get(
    'https://localhost:7001/api/products/101'
);

expect(response.status()).toBe(200);

const product =
    await response.json() as ProductResponse;

expect(product.id).toBe(101);
expect(product.name).toBe('Laptop');
```

Important mentor concept: TypeScript interfaces provide compile-time checking. They do not automatically validate incoming JSON at runtime. For untrusted API responses, introduce runtime schema validation as the framework matures.

## 11. Build a reusable API Client

Mentor: If you have 100 API test cases, should every test contain the complete API URL?

Student: No, Sir. We should create a reusable API client.

Create `utils/ProductApiClient.ts`.

```
import {
    APIRequestContext
} from '@playwright/test';

import { Product } from '../testdata/Product';

export class ProductApiClient {

    constructor(
        private request: APIRequestContext
    ) {}

    async getAll() {

        return await this.request.get('/api/products');
    }

    async getById(id: number) {

        return await this.request.get(
            `/api/products/${id}`
        );
    }

    async create(product: Product) {

        return await this.request.post(
            '/api/products',
            {
                data: product
            }
        );
    }

    async update(id: number, product: Product) {

        return await this.request.put(
            `/api/products/${id}`,
            {
                data: product
            }
        );
    }

    async delete(id: number) {

        return await this.request.delete(
            `/api/products/${id}`
        );
    }
}
```

Now our test becomes cleaner:

```
import { test, expect } from '@playwright/test';

import { ProductApiClient }
    from '../utils/ProductApiClient';

test('Verify product API', async ({ request }) => {

    const api = new ProductApiClient(request);

    const response = await api.getAll();

    expect(response.status()).toBe(200);

});
```

This is a practical example of encapsulation and abstraction in TypeScript.

## 12. Configure Base URL

Instead of repeating the API URL in every test, configure it centrally.

`playwright.config.ts`

```
import { defineConfig } from '@playwright/test';

export default defineConfig({

    testDir: './tests',

    use: {
        baseURL: 'https://localhost:7001'
    },

    reporter: [
        ['list'],
        ['html']
    ]

});
```

Now tests can use relative paths:

```
const response = await request.get('/api/products');
```

For a local development server using an untrusted HTTPS certificate, configure the test environment to trust the development certificate where possible. Playwright also supports `ignoreHTTPSErrors: true` for controlled test environments; avoid using it as a production security workaround.

## 13. Understand API Test Scenarios expected from an SDET

| Test scenario            | Expected result  |
| ------------------------ | ---------------- |
| GET all products         | 200 OK           |
| GET existing product     | 200 OK           |
| GET missing product      | 404 Not Found    |
| POST valid product       | 201 Created      |
| POST invalid product     | 400 Bad Request  |
| PUT existing product     | 200 OK or 204    |
| DELETE existing product  | 204 No Content   |
| Unauthorized API request | 401 Unauthorized |
| Forbidden operation      | 403 Forbidden    |

These are typical expected contracts. The actual response should match your application's API design.

# 14. Advanced SDET Concept – Authentication Token Testing

Now let's introduce an enterprise scenario.

Suppose our ASP.NET Core API requires JWT authentication.

```
       Playwright API Test
               |
               v
       POST /api/auth/login
               |
               v
       Authentication API
               |
               v
       Validate Credentials
               |
               v
       JWT Access Token
               |
               v
       Playwright Stores Token
               |
               v
       GET /api/products
               |
               | Authorization:
               | Bearer JWT
               v
       Protected Product API
               |
               v
       HTTP 200 OK
```

Example:

```
test('Access protected product API', async ({ request }) => {

    const loginResponse = await request.post(
        '/api/auth/login',
        {
            data: {
                username: 'admin',
                password: 'Admin@123'
            }
        }
    );

    expect(loginResponse.status()).toBe(200);

    const loginData = await loginResponse.json();

    const token = loginData.token;

    const productResponse = await request.get(
        '/api/products',
        {
            headers: {
                Authorization: `Bearer ${token}`
            }
        }
    );

    expect(productResponse.status()).toBe(200);

});
```

This assumes the authentication API returns a `token` property. Use test-only credentials and never commit real secrets to Git.

# 15. UI Testing + API Testing Together

This is where SDET engineering becomes interesting.

Imagine we want to test the complete shopping experience.

Instead of creating products manually through the UI, we can create test data using the API and then verify it through the browser.

```
             PLAYWRIGHT TEST
                    |
          +---------+---------+
          |                   |
          v                   v
       API TEST             UI TEST
          |                   |
          v                   v
      Create Product      Open Gallery
          |                   |
          v                   v
      MySQL DB             Select Product
          |                   |
          +---------+---------+
                    |
                    v
              Shopping Cart
                    |
                    v
             Verify Product
                    |
                    v
              PASS / FAIL
```

Example testing strategy:

1. Use API to create a test product.
2. Open the browser.
3. Navigate to Product Gallery.
4. Search for the newly created product.
5. Add it to the cart.
6. Verify the product name and price.
7. Complete checkout.
8. Use API to verify order creation.

This is called API-assisted UI testing.

It reduces unnecessary UI setup and helps build faster, more reliable end-to-end tests.
