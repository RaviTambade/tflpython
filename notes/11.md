# 4. First Principle — What Makes an Object "Unused"?

This is the most important concept. Consider:

```python
policy = InsurancePolicy("POL1001", "Ravi", 1000000 )
```

We have:

```text
policy ───────────► InsurancePolicy
```

The object has a reference.

Now:

```python
another_policy = policy
```

We get:

```text
policy ───────┐
              ▼
        InsurancePolicy
              ▲
              │
another_policy┘
```

There are now **two references** to the same object. This leads us to an important Python concept:

# Reference Counting

 

# 5. Reference Counting

Python implementations such as **CPython** use reference counting as a primary mechanism for managing object lifetime. Think of every object as having a counter:

```text
Reference Count
       │
       ▼
How many references currently point to this object?
```

Example:

```python
policy = InsurancePolicy("POL1001", "Ravi", 1000000)
```

Conceptually:

```text
policy
   │
   ▼
+----------------------+
| InsurancePolicy      |
| Ref Count ≈ 1        |
+----------------------+
```

Now:

```python
another_policy = policy
```

Conceptually:

```text
policy ──────────┐
                 ▼
        +----------------------+
        | InsurancePolicy      |
        | Ref Count ≈ 2        |
        +----------------------+
                 ▲
                 │
another_policy ──┘
```

There are two references to the same object.

 

# 6. Removing a Reference

Now:

```python
del policy
```

The reference `policy` is removed.

But:

```text
another_policy
       │
       ▼
InsurancePolicy
```

still exists. So the object is still reachable. Now:

```python
del another_policy
```

There are no remaining references from these variables. Conceptually:

```text
Reference Count → 0
```

The object can now be reclaimed.

 

# 7. Classroom Demonstration

Let's demonstrate references.

```python
import sys

policy = {
    "policy_id": "POL1001",
    "customer": "Ravi",
    "coverage": 1000000
}

print(sys.getrefcount(policy))
```

You may see a value such as:

```text
2
```

Why not `1`? Because `sys.getrefcount()` itself temporarily creates another reference while obtaining the count. So don't treat the exact number as a simple "number of variables." The important learning is:

> **An object can have multiple references pointing to it.**

 

# 8. Mentor Question

# 10. But There Is a Problem...

Reference counting works beautifully in many situations. But consider:

```python

    pass

    pass
```

Look at the relationship:

```text

   │
   ▼
 Policy
   │
   ▼

```

More clearly:

```text

                  │
                  │ policy
                  ▼
               Policy
                  │

                  ▼
               Customer
                  ▲
                  │

```

The objects refer to each other. This is called a:

# Circular Reference

 

# 11. Circular Reference in TFLInsurance

Let's make the example even more realistic.

```python
class Customer:
    pass


class InsurancePolicy:
    pass


customer = Customer()
policy = InsurancePolicy()

customer.policy = policy
policy.customer = customer
```

Now:

```text
Customer
   │
   │ policy
   ▼
Policy
   │
   │ customer
   ▼
Customer
```

Suppose we execute:

```python
del customer
del policy
```

The variables are gone.

But the objects may still reference each other:

```text
Customer ─────► Policy
    ▲             │
    │             │
    └─────────────┘
```

So simple reference counting alone is not enough to identify this unreachable cycle.

# 12. Python's Cyclic Garbage Collector

This is where Python's cyclic garbage collector helps. Think of it as a second-level cleanup mechanism.

```text
              Python Memory Management
                       │
             ┌─────────┴─────────┐
             ▼                   ▼
     Reference Counting     Cyclic GC
             │                   │
             ▼                   ▼
      Ref count reaches      Finds unreachable
           zero?                 cycles
             │                   │
             ▼                   ▼
       Reclaim object       Reclaim cycle
```

So the simplified mental model is:

> **Reference counting handles many objects immediately.
> Cyclic GC helps detect unreachable reference cycles.**

 

# 13. Generational Garbage Collection

Now another question: “Does Python inspect every object every time it performs cyclic garbage collection?” That would be expensive. Imagine TFLInsurance has:

```text
10 customers
100 policies
1,000 claims
10,000 transactions
100,000 temporary objects
```

Checking everything continuously would consume CPU. Python therefore uses a **generational approach** for cyclic garbage collection. The classic teaching model is:

```text
Generation 0
    │
    │ survives
    ▼
Generation 1
    │
    │ survives
    ▼
Generation 2
```

The basic assumption is: **Many newly created objects become unreachable relatively quickly.**

# 15. Why Generations?

Think about TFLInsurance customers. Some data is temporary:

```text
API request
temporary calculation
temporary JSON
```

Some data is long-lived:

```text
Customer
InsurancePolicy
InsuranceProduct
Agent
```

We don't want to treat every object as equally likely to become garbage. So generational GC follows the general idea:

```text
New objects
    │
    ▼
Check frequently
    │
    ▼
Objects that survive
    │
    ▼
Check less frequently
```

This can reduce unnecessary garbage-collection work.

 

# 16. The `gc` Module

Python provides the `gc` module for interacting with the cyclic garbage collector.

```python
import gc
```

For example:

```python
gc.collect()
```

requests a garbage-collection cycle.

Example:

```python
import gc

collected = gc.collect()

print("Objects collected:", collected)
```

The returned value is the number of objects collected by that collection, if any.

 

# 17. Checking Garbage Collector State

You can inspect the GC configuration:

```python
import gc

print(gc.get_threshold())
```

You can inspect collection counters:

```python
print(gc.get_count())
```

You can enable automatic cyclic GC:

```python
gc.enable()
```

And disable it:

```python
gc.disable()
```

But here's an important mentor warning:

> **Don't disable GC simply because you discovered `gc.disable()`.**

Understand the application and measure performance before changing memory-management behavior.

 

# 18. Complete TFLInsurance Demonstration

Let's create a simple circular-reference example.

```python

```

The purpose of this example is **not** to predict an exact collection count. The purpose is to understand the lifecycle:

```text

      │
      ▼

      │
      ▼

      │
      ▼

      │
      ▼

      │
      ▼

```

 

# 19. Important Correction — GC Doesn't Mean "All Memory Immediately Returns to the OS"

This is an important professional-level distinction. Students sometimes think:

```text
gc.collect()
      ↓
RAM immediately returns to Windows/Linux
```

That's not necessarily what happens. Garbage collection primarily makes **Python-managed memory available for reuse by the Python process**. The Python memory allocator may retain memory for future allocations instead of immediately returning every byte to the operating system.

Therefore:

> **Object becomes unreachable ≠ operating system immediately gets all corresponding RAM back.**

This distinction becomes important when debugging memory usage in production systems.

 

# 20. Another Important Distinction — `del` Does Not Mean "Destroy Object"

Students often write:

```python
del policy
```

and think: “Sir, I destroyed the policy.” Not exactly. `del` removes a **reference/name**.

For example:

```python
policy1 = policy
```

Then:

```python
del policy
```

does not destroy the object because:

```text
policy1
   │
   ▼
Policy Object
```

still exists.

So remember:

```text
del variable
       │
       ▼
Remove that reference
       │
       ▼
Does object still have references?
       │
    ┌──┴──┐
   Yes    No
    │      │
 Keep    Reclaimable
```

 

# 21. What About `__del__()`?

Python also has a special method:

```python
__del__()
```

Students may ask: “Is `__del__()` the garbage collector?” **No.** `__del__()` is a finalizer method that may be invoked when an object is being finalized, but it is **not the garbage collector itself**.

For example:

```python
class Policy:

    def __del__(self):
        print("Policy object is being finalized")
```

Do not build application logic around an assumption that `__del__()` will run at a particular time. For important resources such as:

```text
Database connections
Files
Network connections
Transactions
```

use explicit resource-management techniques such as context managers:

```python
with open("policy.txt") as file:
    data = file.read()
```

The key lesson:

> **Memory management and resource management are related, but they are not the same thing.**

# 23. Mentor Thinking — Don't Blame GC for Every Memory Problem

Suppose a TFLInsurance API continuously consumes more memory. A beginner might say:  “Sir, Garbage Collection is not working.” Don't jump to that conclusion. A memory problem could come from:

```text
Global collections
       │
       ▼
Objects kept in caches
       │
       ▼
Large lists/dictionaries
       │
       ▼
Long-lived references
       │
       ▼
Unbounded application state
```

If your application still holds a reference:

```text
cache
 │
 ▼
Policy Object
```

the object is still reachable. GC cannot simply delete an object that your application is still using.
So:

> **Garbage Collector cleans garbage.
> It does not decide that your business data is garbage.**

# 25. Interview Questions

### Q1. What is Garbage Collection?

**Answer:**

Garbage collection is an automatic memory-management mechanism that helps reclaim memory occupied by objects that are no longer reachable by the program.

 

### Q2. What is reference counting?

**Answer:**

Reference counting tracks references to objects. When an object's reference count reaches zero, the object can generally be reclaimed immediately in CPython.

 

### Q3. What problem can reference counting alone have?

**Answer:**

It cannot by itself reclaim objects involved in unreachable circular reference cycles.
 
### Q4. What is cyclic garbage collection?

**Answer:**

It is the mechanism that can detect certain unreachable groups of objects that reference one another and reclaim them.

 

### Q5. What is the `gc` module?

```python
import gc
```

It provides interfaces for inspecting and controlling Python's cyclic garbage collector.

 
### Q6. How can you request garbage collection manually?

```python
import gc

gc.collect()
```

 

### Q7. Does `del` immediately destroy an object?

**Answer:**

Not necessarily.

`del` removes a reference/name. The object can be reclaimed when it is no longer reachable.

 

### Q8. What is a circular reference?

Example:

```text
Customer ───► Policy
    ▲            │
    └────────────┘
```

Two or more objects ultimately reference each other, forming a cycle.
