# Singleton Design Pattern 

> **“Don't start with the Singleton code. Start with the problem that demands a Singleton.”**

## 🏦 Imagine a Large Bank

Imagine I take you into a large bank.

There are:

* 20 branches
* 500 employees
* 100,000 customers
* Thousands of transactions every day

I ask the classroom:

**Ravi Sir:**
“How many vaults should contain the bank's central reserve?”

**Student:**
“Sir, one?”

**Ravi Sir:**
“Exactly!”

Why?

Suppose every branch creates its own independent central vault:

```text
                         BANK
                           │
              ┌────────────┼────────────┐
              │            │            │
           Branch A     Branch B     Branch C
              │            │            │
           Vault A      Vault B      Vault C
              │            │            │
          ₹10 Lakh      ₹20 Lakh      ₹15 Lakh
```

Now I ask:

> **Which vault contains the real central balance?**

We have lost our **single source of truth**.

Instead, the bank wants:

```text
                         BANK
                           │
              ┌────────────┼────────────┐
              │            │            │
           Branch A     Branch B     Branch C
              │            │            │
              └────────────┼────────────┘
                           ▼
                    ┌─────────────┐
                    │  ONE VAULT  │
                    │  ₹45 Lakh   │
                    └─────────────┘
```

This is the basic idea behind the **Singleton Design Pattern**.

---

# 🧠 First Principle — What Is an Object?

Before understanding Singleton, understand object creation.

```python
class BankVault:
    pass

vault1 = BankVault()
vault2 = BankVault()
```

Normally Python creates two different objects:

```text
vault1 ───────► Object #1

vault2 ───────► Object #2
```

Therefore:

```python
print(vault1 is vault2)
```

produces:

```text
False
```

But Singleton wants:

```text
vault1 ───────┐
              │
              ▼
          ONE OBJECT
              ▲
              │
vault2 ───────┘
```

So:

```python
vault1 = BankVault()
vault2 = BankVault()

print(vault1 is vault2)
```

should produce:

```text
True
```

```text
      OBJECT
```

# 🐍 Understanding `__new__()`

Here Python gives us an important lesson.

Beginners often learn:

```python
__init__()
```

and think:

> "`__init__()` creates the object."

Not exactly.

Python conceptually separates **object creation** from **object initialization**.

```text
BankVault()
     │
     ▼
  __new__()
     │
     ▼
Object created
     │
     ▼
  __init__()
     │
     ▼
Object initialized
```

So if we want to control **whether a new object should be created**, `__new__()` becomes important.

---

# 🏦 Building Our Bank Vault

Let's build it step by step.

```python
class BankVault:

    __instance = None

    def __new__(cls, *args, **kwargs):

        if cls.__instance is None:
            print("Creating the vault...")
            cls.__instance = super().__new__(cls)

        return cls.__instance

    def __init__(self):
        self.balance = 1000000
```

Now:

```python
vault1 = BankVault()
vault2 = BankVault()
```

What happens?

### First call

```python
vault1 = BankVault()
```

Python reaches:

```python
__new__()
```

At this moment:

```text
__instance = None
```

So Python creates the object:

```text
__instance
     │
     ▼
┌─────────────────┐
│   BankVault     │
│   balance       │
│   ₹10,00,000    │
└─────────────────┘
```

---

### Second call

Now:

```python
vault2 = BankVault()
```

Python reaches `__new__()` again.

But:

```python
cls.__instance
```

already exists.

Therefore:

```python
if cls.__instance is None:
```

is `False`.

Python returns the existing object.

```text
vault1 ──────────┐
                 │
                 ▼
          ┌──────────────┐
          │  BankVault   │
          │ ₹10,00,000   │
          └──────────────┘
                 ▲
                 │
vault2 ──────────┘
```

Therefore:

```python
print(vault1 is vault2)
```

Output:

```text
True
```

---

# 🔍 `==` vs `is`

This is an excellent opportunity to teach an important Python concept.

```python
vault1 == vault2
```

checks **equality**.

Whereas:

```python
vault1 is vault2
```

checks whether both variables refer to the **exact same object**.

For Singleton, this is the meaningful test:

```python
print(vault1 is vault2)
```

Output:

```text
True
```

# 💰 Shared State

Now let's perform a banking transaction.

```python
vault1.balance = 1000000

vault2.balance += 50000

print(vault1.balance)
```

Output:

```text
1050000
```

Why?

Because there aren't two vaults.

There is only **one object**.

```text
vault1 ──────┐
             │
             ▼
       ┌─────────────┐
       │ ONE VAULT   │
       │ ₹10,50,000  │
       └─────────────┘
             ▲
             │
vault2 ──────┘
```

Changing the object through `vault2` changes the same object observed through `vault1`.

---

# ⚠️ An Important Python Problem

Now I would stop the class and ask:

**Ravi Sir:**

“Is our Singleton implementation completely safe?”

Look carefully at:

```python
def __init__(self):
    self.balance = 1000000
```

Remember:

```text
__new__()  → controls object creation

__init__() → initializes the object
```

Even if `__new__()` returns the same object, `__init__()` can run again when we call:

```python
BankVault()
```

So:

```python
vault1 = BankVault()

vault1.balance += 50000

vault2 = BankVault()

print(vault2.balance)
```

can produce:

```text
1000000
```

because the same object was initialized again.

That teaches us a deeper lesson:

> **Singleton is not merely about returning the same object. The object's initialization lifecycle also matters.**

One simple approach is to initialize the state only when the singleton object is first created:

```python
class BankVault:

    __instance = None

    def __new__(cls):

        if cls.__instance is None:

            cls.__instance = super().__new__(cls)

            cls.__instance.balance = 1000000

        return cls.__instance
```

Now the initial state is established only during the first creation.

# 🎯 Singleton in One Diagram

```text
                    APPLICATION
                         │
             ┌───────────┼───────────┐
             │           │           │
          Module A    Module B    Module C
             │           │           │
             └───────────┼───────────┘
                         ▼
                ┌────────────────┐
                │   SINGLETON    │
                │     OBJECT     │
                └────────────────┘
                         │
                   Shared State
```

The important idea is:

> **Many references, one object.**

Not:

> Many objects containing the same data.

# 🤔 “But Ravi Sir, Should Everything Be Singleton?”

**No!**

This is one of the most important lessons.

Suppose we have:

```python
class Customer:
    pass
```

We obviously need:

```text
customer1 ───► Customer Object 1
customer2 ───► Customer Object 2
customer3 ───► Customer Object 3
customer4 ───► Customer Object 4
```

Each customer represents a different entity.

If we accidentally make `Customer` a Singleton:

```text
customer1 ──┐
customer2 ──┼──► SAME CUSTOMER
customer3 ──┘
```

Now changing:

```python
customer1.name = "Rahul"
```

could affect what `customer2` sees.

**Disaster!**

So Singleton is not automatically a good design choice.

---

# 🌱 Mentor Wisdom

Remember this rule:

> **Singleton is not about making an object special. It is about controlling object lifetime and ensuring one shared instance where one instance is actually required.**

Possible candidates can include:

* Application-wide configuration
* Certain logging infrastructure
* Shared cache managers
* Resource managers
* Some infrastructure services

But don't blindly make every class Singleton.

---

# 🚨 Singleton Has a Cost

Students often ask:

> “Sir, if Singleton is useful, why don't we make every class Singleton?”

Because global shared state can introduce problems.

Consider:

```text
             ┌────────────┐
Module A ───►│            │
             │ Singleton  │
Module B ───►│            │
             └────────────┘
```

Module A changes something.

Module B unexpectedly sees the changed state.

This can make:

* testing harder
* dependencies less obvious
* code more tightly coupled
* concurrency more complicated
* debugging harder

Therefore:

> **Use Singleton because the business or design requirement demands one shared instance — not simply because you know how to implement it.**

# 🌸 Transflower Mentor Mantra

Don't memorize this code:

```python
class Something:
    ...
```

First ask:

> **“Do I really need only one object?”**

Then:

> **“Who should own it?”**

Then:

> **“Who should be allowed to access it?”**

Only after answering those design questions should you write the implementation.

```text
Problem
   ↓
Requirement
   ↓
Design
   ↓
Object Lifetime
   ↓
Implementation
   ↓
Testing
```

### Remember:

> **First understand the problem → then understand the design → then write the code.**

**That is the developer mindset.**
