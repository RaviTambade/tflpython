# From One Big Program to Modules

Suppose we initially write everything inside:

```text
tflinsurance.py
```

It may contain:

```text
Customer
Policy
Premium
Claim
Payment
Agent
Reports
Authentication
Database
```

As the application grows, this becomes difficult to maintain. Instead, we separate responsibilities.

```text
tflinsurance/
│
├── customers/
│   └── customer.py
│
├── policies/
│   └── policy.py
│
├── premiums/
│   └── premium.py
│
├── claims/
│   └── claim.py
│
├── payments/
│   └── payment.py
│
├── reports/
│   └── report.py
│
└── main.py
```

This is the same principle explained in the source: related functionality should be grouped into separate modules and packages. 

 

# 1️⃣ Module = One Python File

A **module** is simply a Python `.py` file containing reusable code. For TFLInsurance:

```text
policy.py
```

could contain:

```python
class Policy:

    def __init__(self, policy_number, customer_id, premium):
        self.policy_number = policy_number
        self.customer_id = customer_id
        self.premium = premium

    def calculate_premium(self):
        return self.premium
```

Another module could contain:

```text
premium.py
```

```python
class PremiumService:

    def calculate_due(self, premium):
        return premium
```

And:

```text
claim.py
```

```python
class Claim:

    def __init__(self, claim_id, policy_number, amount):
        self.claim_id = claim_id
        self.policy_number = policy_number
        self.amount = amount
```

Now each file has a focused responsibility.

# 2️⃣ Package = Collection of Related Modules

As the source explains, a package organizes multiple related modules into a directory. 

For TFLInsurance:

```text
tflinsurance/
│
├── policy/
│   ├── policy.py
│   ├── policy_service.py
│   └── policy_repository.py
│
├── claim/
│   ├── claim.py
│   ├── claim_service.py
│   └── claim_repository.py
│
├── customer/
│   ├── customer.py
│   ├── customer_service.py
│   └── customer_repository.py
```

Think about it this way:

```text
Module
   ↓
One toolbox

Package
   ↓
A toolbox containing multiple related toolboxes
```

# 3️⃣ Importing Modules

Suppose TFLInsurance has:

```text
policy.py
```

and:

```python
class Policy:
    ...
```

Another program can reuse it:

```python
import policy
```

Then:

```python
p = policy.Policy(
    "POL1001",
    "CUS101",
    25000
)
```

This is the same basic reuse mechanism demonstrated in the source with `calculator.py`. 

# 4️⃣ Import Specific Classes

Instead of:

```python
import policy
```

we can write:

```python
from policy import Policy
```

Then:

```python
policy = Policy(
    "POL1001",
    "CUS101",
    25000
)
```

This keeps the code clean.

# 6️⃣ Example: Policy Package

We could create:

```text
policy/
│
├── __init__.py
├── models.py
├── service.py
└── repository.py
```

### `models.py`

```python
class Policy:

    def __init__(
        self,
        policy_number,
        customer_id,
        policy_type,
        premium
    ):
        self.policy_number = policy_number
        self.customer_id = customer_id
        self.policy_type = policy_type
        self.premium = premium
```

### `service.py`

```python
class PolicyService:

    def calculate_premium(self, policy):
        return policy.premium

    def is_active(self, policy):
        return policy.premium > 0
```

### `repository.py`

```python
class PolicyRepository:

    def get_policy(self, policy_number):
        print(
            f"Fetching policy {policy_number}"
        )
```

Now the responsibilities are separated.

# 7️⃣ Why This Matters in Real Software

The source identifies several benefits of modules: reuse, organization, easier maintenance, faster development and cleaner architecture.  In TFLInsurance, imagine a developer receives this requirement: **"Add a new motor insurance policy."** If the application is properly modularized, the developer knows where to look:

```text
policy/
    models.py
    service.py
    repository.py
```

Instead of searching through:

```text
50000 lines of tflinsurance.py
```

That is the difference between **writing code** and **engineering software**.



# 8️⃣ Modules Support Single Responsibility

The source connects separate modules with the **Single Responsibility Principle (SRP)**.  For TFLInsurance:

```text
customer.py
     ↓
Customer responsibility

policy.py
     ↓
Policy responsibility

premium.py
     ↓
Premium responsibility

claim.py
     ↓
Claim responsibility

payment.py
     ↓
Payment responsibility
```

Don't create:

```text
insurance.py
```

with:

```python
create_customer()
create_policy()
calculate_premium()
process_claim()
make_payment()
generate_report()
send_email()
authenticate_user()
```

That file becomes a **God Module**.

# 9️⃣ External Packages

TFLInsurance doesn't need to reinvent everything. Python has a rich ecosystem of reusable packages. The source demonstrates installing packages using `pip`. 

For example:


Then:

```python

```

TFLInsurance could use external packages for capabilities such as:

```text

Database access

Logging
API clients

```

The principle is:  **Don't reinvent a proven wheel.**
