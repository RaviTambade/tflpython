### File: `app/schemas/policy_schema.py`

Run

```
from pydantic import BaseModel, Field


class PolicyCreate(BaseModel):
    name: str = Field(min_length=2, max_length=100)
    description: str = Field(min_length=5)
    maturity: str
    premium: float = Field(gt=0)


class PolicyUpdate(PolicyCreate):
    pass


class PolicyResponse(PolicyCreate):
    id: int
```

Ravi Sir: Notice that we are using Pydantic for validation, not for managing database operations.

For example, a premium of `-100` will fail validation.

The framework returns HTTP `422 Unprocessable Entity` without requiring us to write manual validation code for this basic constraint.

```
from app.models.policy import Policy


class PolicyRepository:

    def __init__(self):
        self._policies = {
            1: Policy(
                id=1,
                name="Jeevan Labh",
                description="Life insurance savings plan",
                maturity="10 years",
                premium=15000.0
            ),
            2: Policy(
                id=2,
                name="Jeevan Arogya",
                description="Health insurance plan",
                maturity="5 years",
                premium=12000.0
            ),
            3: Policy(
                id=3,
                name="Jeevan Suraksha",
                description="Family protection plan",
                maturity="15 years",
                premium=20000.0
            )
        }

        self._next_id = 4

    def get_all(self):
        return list(self._policies.values())

    def get_by_id(self, policy_id: int):
        return self._policies.get(policy_id)

    def create(self, policy_data: dict):
        policy = Policy( id=self._next_id,**policy_data        )
        self._policies[policy.id] = policy
        self._next_id += 1

        return policy

    def update(self, policy_id: int, policy_data: dict):
        if policy_id not in self._policies:
            return None
        updated = Policy(id=policy_id,**policy_data)
        self._policies[policy_id] = updated
        return updated

    def delete(self, policy_id: int):
        return self._policies.pop(policy_id, None)
```

### File: `app/services/policy_service.py`

Python

Run

```
from dataclasses import asdict

from app.repositories.policy_repository import PolicyRepository


class PolicyService:

    def __init__(self, repository: PolicyRepository):
        self.repository = repository

    def get_all_policies(self):
        policies = self.repository.get_all()

        return [asdict(policy) for policy in policies]

    def get_policy(self, policy_id: int):
        policy = self.repository.get_by_id(policy_id)

        if policy is None:
            return None

        return asdict(policy)

    def create_policy(self, policy_data: dict):
        policy = self.repository.create(policy_data)

        return asdict(policy)

    def update_policy(self, policy_id: int, policy_data: dict):
        policy = self.repository.update(policy_id,policy_data)

        if policy is None:
            return None

        return asdict(policy)

    def delete_policy(self, policy_id: int):
        policy = self.repository.delete(policy_id)

        if policy is None:
            return None

        return asdict(policy)
```

Ravi Sir: Notice something important. Our service does not directly manipulate the Python dictionary. It asks the repository to perform data operations. This separation makes it easier to change storage implementations and test business logic independently.

Run

```
from fastapi import (APIRouter,Depends,HTTPException,Request,status)
from app.schemas.policy_schema import (PolicyCreate,PolicyUpdate,PolicyResponse)
from app.services.policy_service import PolicyService

router = APIRouter(prefix="/api/policies",tags=["Policies"])


def get_policy_service(request: Request) -> PolicyService:
    return request.app.state.policy_service


@router.get("/")
def get_all_policies(service: PolicyService = Depends(get_policy_service)):
    policies = service.get_all_policies()

    return {
        "message": "Policies retrieved successfully",
        "count": len(policies),
        "data": policies
    }


@router.get("/{policy_id}", response_model=PolicyResponse)
def get_policy(policy_id: int,service: PolicyService = Depends(get_policy_service)):
    policy = service.get_policy(policy_id)

    if policy is None:
        raise HTTPException(status_code=404,detail="Policy not found")

    return policy


@router.post("/",status_code=status.HTTP_201_CREATED,response_model=PolicyResponse)
def create_policy(policy: PolicyCreate,service: PolicyService = Depends(get_policy_service)):
    return service.create_policy(policy.model_dump())


@router.put("/{policy_id}", response_model=PolicyResponse)
def update_policy(policy_id: int, policy: PolicyUpdate,service: PolicyService = Depends(get_policy_service)):
    updated = service.update_policy(policy_id,policy.model_dump())

    if updated is None:
        raise HTTPException(status_code=404,detail="Policy not found")

    return updated


@router.delete("/{policy_id}")
def delete_policy(policy_id: int,service: PolicyService = Depends(get_policy_service)):
    deleted = service.delete_policy(policy_id)

    if deleted is None:
        raise HTTPException(status_code=404,detail="Policy not found")

    return {
        "message": "Policy deleted successfully",
        "deleted_policy": deleted
    }
```

Ravi Sir: The receptionist does not calculate insurance premiums, manage storage, or implement database queries. The router focuses on HTTP communication and translates application outcomes into HTTP responses.

### 13. Understanding SOLID Through Our Insurance Story

Ravi Sir: We have successfully separated our application into components. Now let's understand the design principles behind our decisions.

#### S – Single Responsibility Principle

Each component should have one clear responsibility.

```
Router       → HTTP Communication
Schema       → Data Validation
Service      → Application / Business Logic
Repository   → Data Access
Model        → Business Entity
```

If the database changes, we should not need to rewrite our HTTP routes.

#### O – Open/Closed Principle

Our design should allow extensions without repeatedly modifying stable components. For example, we can introduce a MySQL-backed repository while keeping the API contract unchanged.

#### L – Liskov Substitution Principle

If we define a repository contract, any implementation should honor that contract. A MySQL repository should behave consistently with the expected operations of our in-memory repository.

#### I – Interface Segregation Principle

Avoid forcing a component to depend on operations it does not need. For example, a policy-reading component should not need unrelated payment-processing methods.

#### D – Dependency Inversion Principle

High-level business logic should depend on abstractions rather than being tightly coupled to specific storage implementations. Our current service receives a repository through its constructor:

Python

Run

```
class PolicyService:

    def __init__(self, repository):
        self.repository = repository
```

For a larger application, we can define a Python `Protocol` or abstract base class to formalize the repository contract.

Ravi Sir: We are learning SOLID progressively. We don't need to introduce every abstraction into our first CRUD lab.

### 14. DRY – Don't Repeat Yourself

A student noticed that the original code had repeated lookup logic.

Python

Run

```
for policy in policies:
    if policy["id"] == policy_id:
        return policy
```

Ravi Sir: If the same logic appears in multiple places, changes become harder to manage.

We centralized data access:

Python

Run

```
policy = self.repository.get_by_id(policy_id)
```

The repository owns the lookup implementation. The service reuses it. The router does not need to know how it works.

Ravi Sir: DRY is not about eliminating every repeated line. It is about avoiding duplicated knowledge and behavior that should have one authoritative implementation.
