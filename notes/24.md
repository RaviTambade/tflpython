# Playwright (Browser Automation)

Let us not just learn to automate browsers. Let us learn to understand how software behaves, how users interact with applications, and how to verify that the application works correctly.

Imagine a student developing an online insurance application. The login page looks perfect. The APIs are working. The database stores customer information correctly.

But what happens when a user enters an invalid password, clicks Submit twice, refreshes the page, or opens the application on a different browser?

That is where Browser Automation and Playwright become important.

## 1. What is browser automation?

Browser automation means using a program to control a web browser and perform actions that a real user would perform.

- Open a website.
- Enter username and password.
- Click buttons and navigate pages.
- Verify messages and results.
- Capture screenshots.
- Execute regression tests automatically.

For example, instead of manually testing a login page 100 times, we write a test script and let the browser execute those steps.

## 2. What is Playwright?

Playwright is an open-source browser automation framework developed by Microsoft. It supports browser automation and end-to-end testing across Chromium, Firefox and WebKit, with language bindings including Python, JavaScript, TypeScript, Java and .NET. Think of Playwright as a virtual tester that interacts with your application through a real browser engine.

## 4. How does it work?

1. *Test script*: The tester writes test instructions using Python with pytest or TypeScript with Playwright Test.
2. *Playwright API*: The script locates elements, enters data, clicks buttons, navigates pages and checks expected results.
3. *Browser engine*: Playwright controls Chromium, Firefox or WebKit to execute browser interactions.
4. *Web application*: The browser renders the UI. User actions may trigger API calls, business logic and database operations.
5. *Assertions*: Playwright verifies the observable outcome, such as a success message, dashboard heading or validation error.

## 6. Mentor's important distinction

- *pytest / Playwright Test*: Runs and organizes test cases.
- *Playwright API*: Provides browser-control and assertion capabilities.
- *Browser engine*: Executes browser behavior and renders the application.
- *Web application*: Contains the frontend, backend, business rules and data.

Remember: Playwright does not directly test every internal database operation by default. It tests the user-visible workflow through the browser; API tests and database-level checks can complement it. Understand the architecture first, write the test second, and automate the workflow third.

## 7. Our first hands-on lab

Let's build a small browser automation test using Python and Playwright.

### Step 1 — Install the tools

```
python -m venv .venv
```

Activate the virtual environment on Windows:

```
.venv\Scripts\activate
```

Install Playwright and pytest:

```
pip install pytest playwright
```

Install the Chromium browser:

```
playwright install chromium
```

### Step 2 — Create the test file

Create `test_browser.py`.

```
from playwright.sync_api import sync_playwright


def test_home_page():
    with sync_playwright() as p:
        browser = p.chromium.launch(headless=True)

        page = browser.new_page()
        page.goto("https://example.com")

        assert page.title() == "Example Domain"

        heading = page.locator("h1")
        assert heading.inner_text() == "Example Domain"

        browser.close()
```

### Step 3 — Execute the test

```
pytest -v test_browser.py
```

Expected result:

```
test_browser.py::test_home_page PASSED
1 passed
```

This test opens a browser, navigates to a website, checks the page title and heading, and closes the browser.

## 8. Understand the important Playwright concepts

| Concept      | Purpose                                 | Example                           |
| ------------ | --------------------------------------- | --------------------------------- |
| Browser      | Launches a browser engine               | `p.chromium.launch()`             |
| Page         | Represents a browser tab                | `browser.new_page()`              |
| Locator      | Finds an element on the page            | `page.get_by_role()`              |
| Action       | Interacts with the UI                   | `locator.click()`                 |
| Assertion    | Verifies expected behavior              | `expect(locator).to_be_visible()` |
| Auto-waiting | Waits for elements to become actionable | Built into supported actions      |
| Screenshot   | Captures application state              | `page.screenshot()`               |

Mentor's advice: Avoid fixed delays such as `time.sleep(5)` as your default synchronization strategy. Prefer Playwright's auto-waiting, locator assertions and explicit conditions.

## 9. Real-world testing scenario 


*Module*: Login and Authentication Testing Application: TFLInsurance Testing Framework: Python + pytest + Playwright

The *objective* is to verify that authentication works correctly, invalid users cannot log in, input validation is enforced, and protected pages remain secure after logout.

## 1. Test case documentation

| Test Case ID | Scenario                    | Test Steps                                                                     | Expected Result                                       |
| ------------ | --------------------------- | ------------------------------------------------------------------------------ | ----------------------------------------------------- |
| TC_LOGIN_001 | Valid credentials           | Enter valid username and password; click Login.                                | User reaches the dashboard.                           |
| TC_LOGIN_002 | Invalid password            | Enter a valid username and incorrect password; click Login.                    | Error message appears; user remains unauthenticated.  |

## 10. Detailed test cases

#### TC_LOGIN_001 — Valid credentials

Precondition: User account exists and is active.

1. Open the login page.
2. Enter a valid username.
3. Enter a valid password.
4. Click Login.
5. Verify the dashboard is displayed.

Expected: Successful authentication and dashboard access.

#### TC_LOGIN_002 — Invalid password

Precondition: A valid username exists.

1. Open the login page.
2. Enter a valid username and incorrect password.
3. Click Login.
4. Verify the error message.
5. Verify the user is not authenticated.

Expected: Authentication fails, an appropriate error appears, and protected content remains inaccessible.

#### TC_LOGIN_003 — Empty input fields

1. Open the login page.
2. Leave both fields empty.
3. Click Login.
4. Check the validation messages.

Expected: Required-field validation appears and authentication does not succeed.

#### TC_LOGIN_004 — Session and navigation

1. Log in with valid credentials.
2. Open a protected page.
3. Click Logout.
4. Attempt to open the protected URL directly.
5. Verify access is denied or the user is redirected to login.

Expected: Logout invalidates the authenticated session; protected resources cannot be accessed using the logged-out session.

## 11. Implement the scenarios using Playwright and pytest

The following examples assume your application provides the routes `/login` and `/dashboard`, accessible fields labelled `Username` and `Password`, and a button labelled `Login`. Adjust the selectors and expected messages to match your actual application.

```
# tests/test_login.py

from playwright.sync_api import Page, expect

def test_valid_credentials(page: Page):
    page.goto("http://localhost:8000/login")

    page.get_by_label("Username").fill("valid_student")
    page.get_by_label("Password").fill("valid_test_password")
    page.get_by_role("button", name="Login").click()

    expect(page).to_have_url("http://localhost:8000/dashboard")
    expect(page.get_by_role("heading", name="Dashboard")).to_be_visible()


def test_invalid_password(page: Page):
    page.goto("http://localhost:8000/login")

    page.get_by_label("Username").fill("valid_student")
    page.get_by_label("Password").fill("wrong_password")
    page.get_by_role("button", name="Login").click()

    expect(page.get_by_role("alert")).to_contain_text("Invalid credentials")
    expect(page).to_have_url("http://localhost:8000/login")


def test_empty_input_fields(page: Page):
    page.goto("http://localhost:8000/login")

    page.get_by_role("button", name="Login").click()

    expect(page.get_by_label("Username")).to_be_visible()
    expect(page.get_by_label("Password")).to_be_visible()

    # Verify the application-specific required-field
    # messages or native HTML validation behavior.


def test_protected_page_after_logout(page: Page):
    # Use the application's real login flow or a
    # properly configured authenticated test fixture.
    page.goto("http://localhost:8000/login")

    page.get_by_label("Username").fill("valid_student")
    page.get_by_label("Password").fill("valid_test_password")
    page.get_by_role("button", name="Login").click()

    expect(page).to_have_url("http://localhost:8000/dashboard")

    page.get_by_role("button", name="Logout").click()
    page.goto("http://localhost:8000/dashboard")

    expect(page).to_have_url("http://localhost:8000/login")

```

Important: The logout test assumes the dashboard URL redirects to login after logout. Some applications return `401 Unauthorized` or `403 Forbidden` through their APIs instead. Verify both the UI behavior and server-side authorization where appropriate. Use a dedicated test account and avoid committing real credentials.

## 13. Mentor's assessment checklist

- Positive testing — valid credentials.
- Negative testing — invalid credentials.
- Validation testing — empty fields.
- Security testing — logout and protected routes.
- Automation testing — assertions verify actual outcomes.
- Regression testing — run the tests after application changes.

Transflower mentor takeaway: A test case describes what must be verified. Playwright automates how it is verified. A reliable test suite checks not only whether login succeeds, but also whether unauthorized access is prevented.

```
                    / \

                  / UI  \ 
                 / /E2E  \

               / Playwright\
              /------------ \
             /               \
            / API INTEGRATION \

        /                         \
       /      UNIT TESTS           \
      /   pytest · Business         \
     /         Logic                 \
```

A strong quality strategy combines:

- *Unit testing*: Does the function work?
- *API testing*: Does the endpoint behave correctly?
- *Browser automation*: Can a real user complete the workflow?
- *CI/CD*: Do these checks run automatically whenever code changes?
